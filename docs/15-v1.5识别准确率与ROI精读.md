# v1.5：校验位自校验 + ROI 二次精读

> 来源：`docs/14-识别率提升方案调研.md` 里评估出的两个 P0 项，本次落地。
> 版本 **1.5.0（versionCode 10）**。

## 一、为什么是这两项，而不是换识别库

调研结论是**不换库**：ML Kit 17.3.0 已是打包版最新，免费 + 完全离线这条线里它就是上限；
更强的 Dynamsoft / Scandit 是商业授权，不符合项目性质。

真正的瓶颈在**管线**，不在库：

| 码制 | ML Kit 官方最小要求 | 1080p 全帧里一个占宽 5% 的 EAN-13 |
|---|---|---|
| 通用最小单元 | ≥ 2 px | — |
| **EAN-13** | 整码 ≥ 190 px 宽 | 只有 **96 px**，**不到要求的一半** |
| **PDF417** | 整码 ≥ 1156 px 宽 | 更不够 |

也就是说：码在输入图里占多大比例本身就是识别条件之一。
要救那个 EAN-13，全帧得提到 3840px 以上；而把它所在的一小块裁出来放大，
解码器只需处理 0.1~0.3M 像素，**代价差一个数量级**。这就是 ROI 精读的立足点。

## 二、P0-2：校验位自校验（`domain/ChecksumVerifier.kt`）

### 解决的是「误识」而不是「漏识」

用户说的是「提高识别**准确率**」，这个词有歧义。盘点场景里两者代价完全不同：

| | 后果 | 补救成本 |
|---|---|---|
| 漏识 | 少了一条记录 | 抬手补扫一次 |
| **误识** | 错误数据直接写进库存 | 事后对账，可能已经发错货 |

免费方案确实会误识——ML Kit 在密集 1D 码上偶有一两位数字解错（1↔7、6↔8、0↔8 这类形近误判）。
好消息是 EAN / UPC 系列自带校验位，一次加权和就能挡掉绝大多数。

### 覆盖范围（尽量做小、做准）

| 码制 | 校验方式 | 是否实现 |
|---|---|---|
| EAN-13 | mod-10 加权（12 + 1） | |
| EAN-8 | mod-10 加权（7 + 1） | |
| UPC-A | mod-10 加权（11 + 1） | |
| UPC-E | mod-10 加权（7 + 1） | |
| Code-128 | mod-103 | 见下 |
| Code-39 | mod-43（**可选**） | 见下 |
| QR / Data Matrix | 内建 Reed-Solomon | 库已保证 |

Code-128 为什么不做：它的校验是 `(起始符 + Σ i×符号值) mod 103`，
而**符号值**是 Code A/B/C **子集**的编码值，ML Kit 只给我们**解码后的文本**——
校验符已在校验过程中被吃掉，子集信息也丢了。纯数字串用 Code B 和 Code C 编出来的
符号序列与校验位都不同，无法反推。

硬做只能「B、C 都试一遍，有一个对上就算过」——那会把检出能力削掉一大半，
换来的是「看起来验过了」的假安全感。**不如不做**：返回 `NOT_APPLICABLE` 明确放行，
而不是假装校验过。

### 三态结果，不是布尔

`CheckResult = VALID | INVALID | NOT_APPLICABLE`

`NOT_APPLICABLE`（没法验）与 `VALID`（验过且通过）在调用方看来都是「放行」，
但**语义完全不同**。混成一个 `true` 会让人误以为「所有进来的码都验过了」，
将来排查误识问题会被这个假象带偏。

### 接入位置：**排在所有判定之前**

`ScanViewModel.onCodesDetected` 里的顺序是
校验位 → 准入规则 → 同帧去重 → 时间窗判定。

放在最前面，是因为它筛掉的是**解错的码**：一个解错一位的 EAN-13 不该进入后面的
规则过滤、不该刷新去重时间戳、更不该被写进列表。

这条通路同时覆盖**相册识别**（`decodeFromGallery` 最终也汇到 `onCodesDetected`），
不需要在两处各写一遍。

### 默认开启 + 逃生舱

默认 `ENFORCE`（开）：纯算术、零性能代价，没有理由不开。
保留 `OFF` 是为了万一将来发现某个码制的校验实现有问题，用户能立刻自行退回旧行为，
而不用等下一个版本——这比「相信实现永远正确」更可靠。

### 已知局限（写在代码注释里，不藏）

mod-10 对某些相邻位互换是无感的（算法本身的已知局限）。
所以它是「大幅降低误识」，**不是「杜绝」**。

## 三、P0-1：ROI 二次精读（`domain/RoiPlanner.kt` + `camera/BarcodeAnalyzer.kt`）

### 管线：两段式

```
粗检（全帧 → ML Kit）
    │
    ├─ 已解出码 → 直接走快路径，**多一步都不做**
    │
    └─ 只有「疑似条码但未解码」的候选框 → ROI 精读
            ① 从候选框外扩 25%（留静区）
            ② 逆变换回**原始缓冲区**坐标
            ③ 从 Y plane 直接裁一块灰度图（不做全帧 YUV→ARGB）
            ④ 放大到长边 800px（只放大，不缩小）
            ⑤ 再解一次 → 合并进结果
```

每帧**最多精读一个候选**，取面积最大的那个（它在画面里更靠前，更可能是用户对准的目标）。
多裁几个会让单帧耗时线性上涨，而连扫体验对延迟很敏感。

### 最容易写错的地方：坐标系不是同一个

ML Kit 返回的 `boundingBox` 是**按旋转角摆正之后**的图像坐标；
而能从 `ImageProxy` 的 Y plane 上裁的，是**原始缓冲区**坐标。

两者在 `rotationDegrees = 90 / 270` 时不仅原点不同，宽高还是互换的。

所以 4 个角都要逐点逆变换、再重新求包围盒，不能拿摆正坐标系的 w/h 直接去裁。

推导（`toBufferedCoords`）：

```
摆正：r=0  : (x,y) = (xo,yo)
      r=90 : (x,y) = (H-1-yo, xo)
      r=180: (x,y) = (W-1-xo, H-1-yo)
      r=270: (x,y) = (yo, W-1-xo)

逆解：r=0  : (xo,yo) = (x, y)
      r=90 : (xo,yo) = (y, H-1-x)
      r=180: (xo,yo) = (W-1-x, H-1-y)
      r=270: (xo,yo) = (W-1-y, x)
```

拿 90 度验证取值：摆正后尺寸是 `H×W`，故 `x∈[0,H)`、`y∈[0,W)`；
代入得 `xo = y ∈ [0,W)` ✓、`yo = H-1-x ∈ [0,H)` ✓ —— 正好落回原始缓冲区。

这是整条链路上唯一「错了也不报错、只是识别率莫名其妙变差」的一步，
所以它被拆成纯函数、单独测（`RoiPlannerTest` 20 个用例）。

### 为什么不自己旋图

裁出来的小块**仍处于原始方向**，把相机旋转角原样交给
`InputImage.fromBitmap(bitmap, rotationDegrees)` 让 ML Kit 自己去摆正。

这样既省掉一次全帧旋转，也避开了「自己旋图 + 自己算偏移」这个最容易写错的地方。

### 为什么只读 Y plane

`imageProxy.toBitmap` 会把**整帧**做一次 YUV→ARGB 转换（1920×1080 就是 8MB 分配 +
逐像素插值），再裁掉其中 95% 扔掉——本末倒置。

只读 Y plane（亮度通道）的三个理由：
1. 条码识别本来就不需要颜色信息；
2. 跳过 U/V 两个 plane 的采样与色度插值，开销降到零头；
3. 只处理 ROI 那块区域，1920×1080 里取 200×120 的框，数据量差两个数量级。

用**绝对索引** `buffer.get(i)` 而不是先 `position` 再 `get`：
绝对读取不改变缓冲区游标，即便别处也在读同一块缓冲区也不会互相干扰。

### 两个数值取舍

| 常量 | 值 | 理由 |
|---|---|---|
| `PADDING_RATIO` | 0.25 | ML Kit 的候选框贴得很紧，有时比真实码还小。不外扩会把**静区**切掉——静区丢了 1D 码基本解不出来 |
| `TARGET_LONG_SIDE_PX` | 800 | 约等于 720p 长边，是「够库用、又不浪费」的档位 |
| `MAX_UPSCALE` | 6× | 放大不创造细节，超过这个倍数纯属插值糊弄，还费内存 |
| `MIN_VIABLE_SIDE_PX` | 24 | 这么小的框放大 6 倍也到不了 190px，白花一次识别时间 |

### 一个被测试逼出来的设计修正

初版对「输出长边超过上限」的处理是**先放大再缩回去**。
`RoiPlannerTest` 的两个用例把这个兜底逻辑暴露成问题：它会把 `scale` 压到 1 以下，
等于把细节主动丢掉，还让 `MAX_UPSCALE` 的语义变含糊。

改成**直接拒绝**（返回 `null`）：这种框已经大到接近全帧，全帧本身就在走快路径，
精读没有意义。拒绝比凑合更诚实。

### 线程模型：这个不能写错

ROI 精读要**同步等待** ML Kit 的结果（`Tasks.await`）。

- 精读跑在分析 Executor（`analyzerExecutor`）上——它不是主线程；
- ML Kit 的 `addOnCompleteListener` **显式指定**在同一个 executor 上执行。
  留在默认的（主线程）回调上会**直接卡住 UI**。

背压闸门仍是 `imageProxy.close`：精读全程 `imageProxy` 保持打开（Y plane 是数据源），
`finally` 里才释放。配合 `STRATEGY_KEEP_ONLY_LATEST`，CameraX 自动丢中间帧。

精读的任何异常都被 `runCatching` 兜住并当作「没做」——它是加分项，不该吞掉主结果。

## 四、UI 变化（v1.5）

### 设置面板：4 页里改了两页

| 页 | v1.5 变化 |
|---|---|
| 扫码 | 不变 |
| **识别** | 新增「小码精读（放大重扫）」开关 |
| **规则 → 准确** | 改名为「准确」，新增「校验位检查」开关 + 覆盖范围说明 |
| 结果 | 不变 |

为什么把「规则」页改名并合入校验位：两项机制完全不同
（校验位是**码制自带**的数学约束，规则是**用户自定**的白名单），
但用户要解决的问题是同一个——「别让解错的 / 不该要的码进列表」。
按**问题**而不是按实现分页，用户更好找。

校验位做成**开关**而不是两个 radio：取值只有开/关两种，摆两个单选行反而更难认。
枚举保留两态，是为了将来若要加「只记录不丢弃」时不用改数据模型。

### 高度预算：520 → 545dp

新增小码精读后，识别页复算高度升到 **491dp**。520 仍装得下但只剩 29dp 余量，
估算一偏就要滚动，因此抬到 **545dp**（余量 54dp）。

复算结果（`_height_audit.py`，按 Material3 默认排版逐项累加）：

| 页面 | 实际 | 预算 | 余量 |
|---|---|---|---|
| 识别 | 491 | 545 | 54 |
| 扫码 | 449 | 545 | 96 |
| 准确 | 441 | 545 | 104 |
| 结果 | 349 | 545 | 196 |

面板总高 = 210 + 545 = **755dp** ≤ sheet 在 927dp 屏上的上限 **834dp** ✓
小屏 800dp 时：内容区 = 720 − 210 = 510 ≥ 491 ✓

预算与兜底的分工没有变：预算只负责「默认不用滚」，真的超了由内容区的滚动兜住，
不会像 v1.4.3 那样退化成重叠。

## 六、问题记录

### 1. Gradle transform 缓存坏点

`build_apk.py` 首次失败：

```
Could not read workspace metadata from
...\gradle-home\caches\8.9\transforms\<hash>\metadata.bin
```

`transforms` 目录 2743 条里有 2 条缺 `metadata.bin`。清掉这 2 条即可，**不用清整个缓存**。

> 判据：`gradle-home\caches\8.9\transforms\*` 下每个目录都应有 `metadata.bin`，
> 缺的就是坏点。这次先只删了报错里那一条，第二次换成另一条报错——
> 说明要**一次性全扫**，不能只删报出来的那一个。

### 2. 下载服务的白名单在**启动时**读取（v1.4.4 就踩过，这次确认）

出新版后必须重启服务，否则 dist 里已经是 1.5.0、页面仍显示旧版链接。

重启流程：停掉旧的后台任务 → `_serve_ctl.py --stop` → 重新以后台任务跑 `_serve_start.py`。

## 七、仍然没做的（评估后否决）

**WeChatQRCode**（OpenCV 的微信引擎）技术上确实对症——CNN 检测 + 超分辨率，
对复杂 QR 是开源里最强的。但：

- 只支持 QR（盘点是 1D / 2D 混扫）；
- OpenCV 体积 +20~30MB/ABI；
- 需 NDK / JNI 封装，导致**这块逻辑无法单测**（违反本项目的核心工程约定）；
- 网上流传的「98.7% 识别率」「快 300%」都是推广稿，基线不明确，不能采信。

**留作后路**：将来若「复杂二维码」成为主要痛点，可做成「QR 专用增强通道」——
只在 ML Kit 对某候选**连续失败 N 帧**后，对那一小块调它，而不是全帧走两套引擎。

**多帧投票**（同码连续 2~3 帧一致才采纳）也仍在候选列表里，优先级低于已落地的两项。
