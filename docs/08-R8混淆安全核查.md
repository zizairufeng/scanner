# 08 · R8 混淆安全核查报告

> 核查对象：`dist/ScanStock-1.0-release.apk`（R8 混淆 + 资源压缩版本）
> 核查日期：2026-09-17
> 结论：**通过**。release 包不存在由混淆引起的符号解析风险。

---

## 1. 为什么单独做这件事

`verify_apk.py` 验的是**包名 / 权限 / 签名 / 对齐**——都是 APK 的元数据。
release 包开了 R8（`isMinifyEnabled = true`），它带来的风险不在元数据里，而在：

> **运行时按「字符串」去找的类，被 R8 改了名。**

这类问题有三个恶劣性质：

1. **编译期完全无感**——`BUILD SUCCESSFUL`，零 warning；
2. **静态 import 检查也查不出**——类名不是写在代码里的，是写在 manifest 或 native 库里的；
3. **崩了也难查**——崩在 `ClassNotFoundException` / JNI `FindClass` 失败，堆栈里看不到业务代码。

所以必须换个判据：**直接把「靠字符串引用的类名」列出来，逐个到 dex 里点名。**

---

## 2. 判据设计（三类，不能混为一谈）

早期版本的核查脚本把这三类混在一起，导致大量**误报**。区分它们是这份报告可信的前提：

| 类别 | 引用方式 | R8 改名的后果 | 正确判据 |
|---|---|---|---|
| **A · 字符串引用** | `AndroidManifest` 的 `android:name` / `meta-data` 值；native 库 `.so` 里硬编码的类描述符 | **直接崩溃**，且堆栈难查 | release dex 中必须存在**完全同名**的类 |
| **B · 代码引用** | Kotlin/Java 里的 `.class` 字面量、构造调用、接口实现 | **安全**，R8 会同步更新所有引用点 | 原名存在，**或**经 `mapping.txt` 反查到新名且新名存在 |
| **C · 方法调用链** | 方法调用 | 允许改名，**也允许被内联**（R8 把单调用点的简单方法内联后消解原方法） | 同上；两者都不满足时标为「疑内联」，**不算失败** |

## 3. 证据来源

不靠推断，全部来自可复现的机械证据：

| 证据 | 获取方式 | 用途 |
|---|---|---|
| native 库字符串常量池 | 直接扫 `libbarhopper_v3.so` 二进制里的 `Lxxx/yyy/Zzz;` 描述符 | 找出 JNI 按名查找的类 → 构成 A 类清单 |
| `AndroidManifest.xml` | `aapt2 dump badging` / `dump xmltree` | 找出 manifest 按名引用的类 → 构成 A 类清单 |
| `mapping.txt`（33.7 MB） | R8 输出，解析 `旧名 -> 新名` 与成员映射 | B/C 类改名反查 |
| `usage.txt`（3.8 MB） | R8 输出 | 参考（注意：**不能**据它判定「类被删除」，见 §6） |
| `missing_rules.txt` | R8 输出，**仅当它认为缺少必要 keep 规则时才生成** | 判定 R8 是否报告了反射风险 |
| 纯 Python dex 解析 | 自解析 `type_ids` / `method_ids` / `string_ids` 三张表 | 最终事实来源（dex 是实际产物） |

### 4.4 「被内联消解」不等于「功能丢失」——如何证明

R8 会把**单调用点 / 纯函数**形态的类内联进调用方，然后消解掉原类。
此时 `mapping.txt` 里查不到它，但这**不是缺陷**。用两类证据反证：

| 被消解的类 | 反证证据 | 结论 |
|---|---|---|
| `CopyFormatter` | release dex 的**字符串池**中存在 `'序号,码制,内容,时间\n'`（CSV 表头） | 逻辑仍在 |
| `BarcodeAnalyzer` | 其下游调用 `BarcodeScanner.process` 在 release dex 中仍被引用 | 逻辑仍在 |

> 附注：该 CSV 表头在 dex 里是 `'序号,码制,内容,时间\n'`——**带换行**。
> 因为 Kotlin 对 `const val EOL = "\n"` 做了**编译期常量折叠**，
> `"序号,码制,内容,时间" + EOL` 被合并成了单个字面量。

## 5. 核查中发现并加固的一处脆弱依赖

**问题**：`com.google.android.libraries.barhopper.**` 这个包**没有被本项目的混淆规则显式保护**。

它能存活，靠的是官方 `barcode-scanning-17.3.0` AAR 里的一条 consumer rule：

```proguard
-keepclasseswithmembernames class * {
    native <methods>;
}
```

这条规则 keep 所有「声明了 native 方法」的类——barhopper 的类恰好符合，于是被捎带保住了。
**这是间接效果，不是显式契约。**

**处置**：在 `app/proguard-rules.pro` 中补上显式规则（附上了完整理由与 .so 中的原始证据）：

```proguard
-keep class com.google.android.libraries.barhopper.** { *; }
```

**验证**：重新构建后包体积**仍为 22.51 MB**（未增大）——
说明这 5 个类原本就已被保留，新增规则只是把隐式依赖变成显式契约，
防止将来升级 ML Kit 时因依赖链旁枝变化而静默失效。

## 6. 工具自身的 3 个 bug（诚实记录）

这份报告可信度的前提是：**核查工具本身也要被核查**。本次过程中查出并修掉了 3 个导致误报的 bug：

| # | Bug | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | **dex header 偏移读错** | 「全部 21 条调用链中断」，结论惊悚但荒谬 | `method_ids_size/off` 写成了偏移 **80/84**，实际应为 **88/92**（80/84 是 `field_ids`）——等于在读**字段表**去查**方法** | 修正偏移；**新增解析器自检**（查 `java.lang.Object.<init>` 这类必然存在的方法，查不到就拒绝输出结论）+ 表越界断言 |
| 2 | **特征串期望值漏了常量折叠** | 报「CSV 表头字符串丢失」 | Kotlin 把 `"表头" + EOL` 折叠成带 `\n` 的单字面量，精确比对必然失配 | 改用**子串包含**判定 |
| 3 | **臆造了两个不存在的类名** | 报 2 处「类被删除」 | `BarcodeScannerImpl`、`internal.BarcodeScanner` 是我凭记忆写的，**debug（未混淆全集）里也不存在** | 删除假目标；改用真实存在的 `BarcodeRegistrar`；确立「**先查 debug 是否存在，再谈 release 是否丢失**」的判据顺序 |

> 教训：**工具 bug 会伪装成产品缺陷**。
> 这次之所以能发现，是因为坚持了交叉验证——
> 同一个结论用「解析 dex」和「字节级搜索二进制」两条独立路径得出，不一致就说明工具有问题。
> 唯一被采纳的「修产品」而非「修工具」的动作，是 §5 的那条 keep 规则（属加固，非修错）。

## 8. 仍未验证的部分

静态手段已经用尽（含 `.so` 二进制级证据、R8 自身报告、mapping 反查、字符串池比对）。
**仍然无法在本机验证的，全部是真机运行时行为**：

用 `mapping.txt` retrace 即可定位——这正是 §5 那条显式规则想避免的情况。
