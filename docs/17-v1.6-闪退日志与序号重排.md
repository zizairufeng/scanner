# 17 · v1.6：闪退排查用的日志、锁竖屏、删除后序号重排

日期：2026-10-16　｜　版本：1.5.0 → **1.6.0（versionCode 11）**

这一版来自四条反馈：

1. 最近出现闪退，分析一下；不行就下个版本加日志，我把日志发你。
2. 不要自动旋转，固定住。
3. 勿扫删除后，序号自动排序。
4. 局域网在线下载安装功能继续使用。

## 1. 闪退：先分析，再把「说不清」变成「可证伪」

### 1.1 为什么原来的版本查不了闪退

APK 里原本**没有任何可回传的证据**：不联网（INTERNET 被显式移除）、不接 crash 上报、
不进 `dumpstate`。用户能说出口的只有「最近闪退了几次」。这种情况下的"分析"，
本质上是在猜——而闪退的原因 90% 藏在那一次调用的具体参数里，猜不出来的。

所以这一版的重点不是「猜得更准」，而是**把现场留在本机，让用户一键发回来**。

### 1.2 代码走查后，按可疑度排序的几个方向

> 这些是**待验证的假设**，不是结论。每一条都标了「日志里看什么」——
> 拿到用户日志之后应该能直接证实或排除，而不是继续猜。

| # | 可疑点 | 为什么会崩 | 日志里看什么 |
|---|---|---|---|
| A | **旋转屏幕 / 方向变化** | 原 `screenOrientation=fullSensor`，手腕一转就触发 Activity 重建 → CameraX 解绑重绑。重建瞬间 `PreviewView`(TextureView) 的 Surface 被释放、而分析器仍持有 `ImageProxy`，原生层 SurfaceTexture 与重建的竞争**在 Java 层 catch 不到**，表现为偶发闪退 | `MainActivity onCreate（方向=…）` 与 `onDestroy` 的密集分布；崩前是否紧跟着一次 onCreate |
| B | **相册选大图** | `ImageDecoder` 里 `BitmapFactory.decodeStream` 可能抛 `OutOfMemoryError`；`runCatching` 虽然能兜住（Throwable），但此时堆已经很紧张，紧接着 Compose 绘制再要内存就容易二次 OOM | 崩前是否有 `开始识别相册图片` 而没有对应的 `相册识别完成` |
| C | **ROI 精读裁图** | `cropYPlaneToBitmap` 用绝对索引 `buffer.get(pos)`，部分机型 Y plane 是 slice（limit < rowStride×height），越界会抛异常。已被 `catch (t: Throwable)` 兜住，但大 ROI 的 `IntArray` 是真内存开销 | `识别帧异常（已自动恢复）` 出现的频率与机型（日志头部有 ABI / 型号） |
| D | **导出 xlsx** | `XlsxWriter` 全内存构建，几千条时是几十 MB 的峰值 | 崩前是否有 `导出 XLSX 成功`（有则排除） |
| E | **相机被占用 / 无后置镜头** | `bindToLifecycle` 失败，已被 runCatching 兜住 | `识别帧异常` 与 `相机绑定失败` |

**A 已经在这一版里从根上消掉了**（见第 2 节锁竖屏）——它是唯一一条「不需要日志就能确定因果」的改动。
其余四条要靠日志区分。

### 1.3 加了什么

新增 `logging/AppLog.kt` + `ScanStockApp`：

- **事件日志**写 `filesDir/logs/app.log`（512KB 滚动，保留 `app.log.1`）。
  只记**事件**，绝不逐帧记（识别回调 20fps，逐帧写会拖死主链路）。
- **崩溃报告**写 `filesDir/logs/crash-<时间>-<线程>.txt`，内容顺序是
  「版本/设备 → 崩溃线程堆栈 → 完整异常 → 崩溃前 200 行事件日志」。保留最近 5 份。
  异常处理器在 `Application.onCreate` 就装好——**打开就闪退**这类问题必须能在
  第一个 Activity 起来之前就记录下来。
- **一键发送**：主屏顶部横幅（有崩溃时出现）+ 设置 → 数据 → 运行日志 → 「发送日志」。
  把运行日志与全部崩溃报告合并成**一个 txt**，走 `FileProvider` + 系统分享面板发出去
  （不申请任何权限、不联网）。合并成 txt 而不是 zip，是因为用户要在微信里直接点开看。
- **日志里不含扫码内容**：只记「计入 3 条，累计 128 条」这种规模信息，
  不记条码值。这一点在横幅文案里也对用户讲明了，否则他会担心把盘点数据一起发出去。

写日志的三条纪律（都在 `AppLog` 的注释里）：写 `filesDir` 而不是 `cacheDir`（存储紧张时
cache 会被清掉，而崩溃恰恰常发生在存储紧张时）；每行 append 落盘而不是内存缓冲
（进程先没了，缓冲里的日志就没了）；记录崩溃这件事**自己绝不能抛异常**。

## 2. 锁定竖屏

`AndroidManifest` 里 `screenOrientation` 由 `fullSensor` 改成 **`portrait`**。

v1.5 的注释里当时的理由是「货架高位/低位横持更顺手」，这一版推翻了它。原因是实测下来
**旋转的代价远大于收益**：盘点时是单手握着对着货架扫，手腕自然转动就会触发旋转，
每次旋转都要走一遍 Activity 重建 → CameraX 解绑重绑 → 预览黑一下、这一两秒扫不到码，
而且它正是上面 A 类闪退的直接触发条件。

扫码是「取景框居中」的动作，横持时画面不跟着转并不影响对准。

## 3. 删除后序号自动重排

### 3.1 口径变更

v1.5 及以前 `ScanItem.seq` 是**稳定递增**的，删除中间项后**不重排**，
当时的理由是「保证已复制/已导出的数据与屏幕上的序号一一对应」。

这一版按反馈改成**删除后自动重排**，屏幕上的序号恒等于行号（1..N）。
理由是盘点现场的实际用法：删掉误扫的那条之后，用户是**拿屏幕上的序号去核对实物**的，
中间空一个号会让人怀疑「是不是漏扫了一条」。
至于「导出与序号对应」，那是**导出那一刻**的快照语义——导出文件里已经固化了当时的编号，
事后重排不会追溯修改它。

### 3.2 实现要点（三条都不是顺手能改对的）

1. **序号派生，不再维护自增计数器**。新增 `domain/SequenceRenumber.kt`，
   `seq` 一律由列表位置派生。原来的 `nextSeq` 自增变量与列表是两份状态，
   撤销 / 恢复会话时任意一处漏改就会**撞号**，而撞号会让
   `LazyColumn(key = { it.seq })` 直接抛 `Key ... was already used` ——
   这本身就是一类闪退。派生出来就没有这个风险。
2. **撤销凭据从「序号」换成「令牌」**。`UiEvent.UndoableMessage` 原来回传被删条目的
   `seq` 做校验，重排之后那个 seq 立刻就不代表它了。改用独立于列表内容的单调递增
   `token`，语义是「这是第几次删除」，可以正确判断「这条 Snackbar 还是不是最新一次删除的」。
3. **三条入口一起收敛**：删除、撤销、恢复历史会话都过 `SequenceRenumber.renumber()`。
   恢复旧快照时也重排——v1.5 存下来的快照可能带断号，不补的话「序号=行号」这条
   不变量会在恢复的那一刻就破掉。

单测：`SequenceRenumberTest`（7 条），覆盖断号补齐、保持原顺序、保留 qty、
删除两次的连续场景，以及「已连续时返回同一实例」（识别回调每帧都会调一次，不能白拷列表）。

## 4. 局域网下载继续可用

`tools/serve-apk.js`（不进 APK，改它不需要重新出包）这一版修了一处**会静默发错版本**的坑：

原本白名单是**硬编码文件名**的：

```js
['/', { file: 'ScanStock-1.5.0-release.apk', ... }],
```

后果是：出了 1.6.0 的包之后，服务**照样能起来、日志照样正常、下载也照样成功** ——
只是下到的是上一版。这是最难发现的一类故障（一切"正常"，只有版本是错的），
而且每次发版都得记得改代码。

改成**启动时扫描 `dist/` 里匹配 `ScanStock-*.apk` 的文件**，`/` 指向 release（没有则最新）。
安全属性不变：仍然只认 `dist/` 这一层目录下的这个模式，不做目录遍历、不列目录、
未知路径一律 404，`statFile` 里还有一道「解析后的父目录必须等于 ROOT」的兜底。

### 补充：v1.6 之后「打不开下载页面」这件事的两处根因

出包第二天反馈「打不开下载页面」。查下来服务端本身没问题（端口没人监听、地址也正常），
真正的原因是两条**容易被误判**的设计问题，都已修掉：

1. **服务本来就不是常驻的**。它是前台进程，起它的那个窗口一关就停了。
   表现是「昨天还能下、今天打不开」，很容易被当成服务坏了。
   → 加了一键启动脚本 `tools/serve-apk.sh`（自动找 node、自动忽略容器里注入的
   `NODE_OPTIONS`），启动报告里第 1 条就写「本窗口是否还开着」，
   并给出 `nohup` 常驻写法。
2. **默认不绑回环**，所以在电脑本机敲 `http://127.0.0.1:8080/` **必然失败**
   ——而这会被直接误判成「服务没起来」，接着就会去查一堆无关的东西。
   → 默认改成「所有外部网卡 **+ 回环**」，报告里分组打印，回环那组明确标注
   「仅本机自测（手机打不开这个地址）」，既能让用户自证服务状态，又不会误导。

另外，启动报告里直接印了手机连不上时的排查顺序（窗口 → 同 Wi-Fi → AP 隔离 →
防火墙 → 地址敲全），省得每次都来问一遍。

### 实测（本机 2026-10-16）

```
提供目录 : $HOME/WorkBuddy/scan-app/ScanStock/dist
监听 2 个地址（同一份内容、同一个端口），任一条通即可：
  http://192.168.2.233:8080/        ← 手机用这个，本机局域网地址，换机器/换网段会自动变
  http://127.0.0.1:8080/            ← 电脑本机浏览器自测用

启动报告列出 dist/ 里现有的 4 个包（1.5.0/1.6.0 × release/debug），各带 SHA256
GET /                              200  HTML 索引页，含各包 SHA256
GET /ScanStock-1.6.0-release.apk   200  11,609,848 B，下载后 SHA256 与源文件一致
                                    （127.0.0.1 / localhost / 192.168.2.233 三个入口都验过）
GET /ScanStock-1.6.0-release.apk   206  Range 续传正常（r=1000000-1000099 → 100 B）
GET /../etc/passwd                 404
GET /secret.apk                    404
```

> 有一个坑值得记一笔：**别拿 `/tmp` 当下载测试的落地目录**。
> 本机（容器内）`/tmp` 只有 10 MB，11.6 MB 的 APK 下到 `/tmp` 会被静默截断成
> 10,481,664 B，SHA256 对不上，看起来像「服务发错了文件」。换到大盘的目录里再比对就一致了。

启动方式见 `docs/07-APK构建与安装.md`：

```bash
bash tools/serve-apk.sh                                       # 前台
nohup bash tools/serve-apk.sh > /tmp/serve-apk.log 2>&1 &     # 后台常驻
```

> 容器/沙箱里跑过的话会注意到脚本里有一步「忽略注入的 `NODE_OPTIONS`」：
> 那个变量指向宿主 App 的 `node-language-shim.cjs`，在容器里不存在，
> Node 会在启动阶段就 `MODULE_NOT_FOUND` 退出。脚本自动处理，宿主机上也不会误伤。
