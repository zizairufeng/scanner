# v1.8.2 — 把「越难扫越卡」这条链掐断

> 一句话：难扫的码不再让画面变卡，补救链从「最坏 400~700ms」压到「约 220ms」，
> 另外加了中心对准点和自诊断角标，把两类最常见的「扫不出」直接指出来。

## 一、问题是怎么定位的

v1.7/v1.8 加了一堆补救手段（候选框精读、对比度拉伸、第二引擎、中心区补扫、DPM 阶梯），
每个都是「解不出就再试一次」。问题出在这些尝试是串行跑在 ML Kit 的回调线程里的，
而 `imageProxy.close` 在整条链跑完之后才调用。

配合 `STRATEGY_KEEP_ONLY_LATEST`，结果是：

```
一帧进入分析 ──► ML Kit 主趟 ──► ① ──► ② ──► ③ ──► ④ ──► ⑤ ──► close() ──► 才算放行下一帧
                                  └────────── 400~700ms ──────────┘
                                  这段时间新帧全部被丢弃
```

也就是说：码越难扫，实际分析帧率越低（估算 1.5~3fps），而用户看到的是
「越难扫越像卡住」——恰好是最需要帧率的场景。

原来的闸门 [SLOW_PASS_MS] 判的是**单次**尝试超过 150ms 就放弃后续，
但五级里每一级「都没超 150ms」，累起来照样能到 700ms。

## 二、这次改了什么

### 1. 补救链加总预算（P0-1）

新增 `domain/RefineBudget.kt`（纯逻辑，可单测）：整条链共用一个 220ms 的预算，
每开始一级之前先问「剩下的还够不够跑一次」，不够就立刻收手、把这一帧放走。

| | v1.8.1 | v1.8.2 |
|---|---|---|
| 最坏单帧耗时 | 400~700ms | ~220ms（+ 一次尝试的溢出） |
| 最难场景分析帧率 | 1.5~3 fps | ~4.5 fps |
| 正常扫到码的快路径 | 不受影响 | 不受影响（预算只在补救链里用） |

### 2. 有候选框就跳过 DPM 阶梯（P0-2）

DPM 阶梯（反色 + 紧贴裁剪 + 二值化）的前提是「ML Kit 连候选框都没给」。
一旦给了框，说明这是常规可见的码，那套流程对它没用——直接跳过，省掉最贵的一段
（九级裁剪 + 解码）。

### 3. DPM 阶梯改成「轮转扫描」

加了预算之后一轮扫不完九级（约 90ms 只够 3~4 级）。如果每次从第一级开始，
只有小码才需要靠后的级别，就会帧帧在同一个位置被截断、永远扫不到。
所以游标记住「这一轮停在哪」，下一轮接着往下：9 级 / 每轮 3 级 / 间隔 400ms，
最迟 1.2 秒覆盖全部尺寸。

### 4. 中心区补扫不再连坐 DPM 阶梯

以前中心区那 250ms 节流一旦拦下，整个函数提前 return，DPM 也跟着不跑，
实际是两道节流串联（DPM 最快 ~500ms 才动一次）。现在两者各有各的节流。

### 5. 取景框加中心对准点 + 一行提示（P0-3）

ML Kit 官方文档有一条硬约束：Data Matrix 必须压住图像中心点才会被识别。
方码偏出中心时粗检连候选框都不给，「按候选框精读」那条路根本不会启动——
用户以为是不够近，实际是位置错了。

现在取景框中心画了一个空心准星，下方一行小字「方码压在中心 · 四边留白」。
取景框本身**严格居中**（提示是独立叠层带 y 偏移），否则准星就不再可信。

### 6. 自诊断角标：只在真的卡的时候出现

新增 `domain/ScanPerf.kt`：`FrameCostMeter` 用 1 秒滑动窗口统计「完成帧率 + 单帧耗时」，
`ScanPerf.isSlow` 判据是 `帧率 < 10fps` 或 `平均单帧 > 150ms`。慢的时候预览左上角出现：

```
识别 6.2 fps · 单帧 178ms
```

连续 3 个窗口（约 3 秒）恢复才收掉，避免闪烁。

**没有给它开关**，两个理由：仓储场景常驻性能数字是纯噪音；设置面板已经顶到
`ModalBottomSheet` 的高度上限（210 + 610 = 820dp ≤ 834dp），再加一行开关会被裁掉。

它同时是这次优化最诚实的验收标准：优化前对难扫的码会常驻「5fps」，
优化后应当很少出现、出现了数字也该更高。

## 三、代码审查发现并修掉的问题

按 `code-review-bug-diagnosis` 的清单过了一遍，其中四个是真问题：

| 级别 | 问题 | 修法 |
|---|---|---|
| P1 | DPM 游标在「这一级规划不出裁剪块」（尺寸太小）时不推进，预算只够 3 级时帧帧重复这 3 个废级别，后面的真级别永远轮不到 | 先记「走到第几级」再判能不能裁 |
| P1 | 命中后 `lastDpmHitLevel` 一直有效，每轮都从同一级开始，换成别的尺寸的码永远轮不到 | 删掉该变量，游标成为唯一顺序来源；命中即把游标停在命中级 |
| P1 | 关掉「小码精读」会连带关掉 DPM 阶梯（它在函数开头那道 return 之下） | ①~④ 归精读开关，⑤ 归双引擎开关，两者不再连带 |
| P1 | 取景框本该严格居中，若与提示文字放在同一个 Column 里会被顶高约 15dp，准星指向的不是图像中心 | 提示改成独立叠层 `offset(y = 100dp)` |

另外两处措辞纠正（不是 bug，但注释与实现不符）：预算闸门是「开始前判、开跑就跑完」
的上限而不是硬截止；`frameStartedAt` 的起点在 ML Kit 主趟之前而非 `InputImage` 构造之前。

## 四、验收

- 单测 240/240 通过（+24）：`RefineBudgetTest`（8）、`ScanPerfTest`（12）、
  `RoiPlannerDpmLadderTest` 补轮转顺序与「每轮被截断仍覆盖全部级别」（4）。
  其中最有价值的一条是「每轮只试 3 级，三轮必须覆盖全部 9 级」——它锁住的正是
  「小码迟早会被扫到」这个不报错的活锁。
- 版本 `versionCode 15 / versionName 1.8.2`；权限未变（CAMERA + VIBRATE）。
- **未真机实测**：1.5fps → 4.5fps 是按时长估算的，实际数字要看角标；
  角标出现的频率、中心提示的可读性也需要上手看。
