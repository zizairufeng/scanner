# v1.8.10 — 崩溃日志提示反复弹出：忽略状态没有持久化

> 用户反馈：「崩溃的日志我忽略了，还是会一直弹出，帮我检查清楚后修复。」
>
> 结论：**不是又崩了一次，而是「忽略」这个动作根本没被记住**。
> 它只改了 ViewModel 里的一个内存布尔值；磁盘上的崩溃报告一份没删、也没记已读。
> 进程一重启（冷启动、或崩溃后被系统拉起），布尔值回到默认值，
> 而报告文件还在（最多留 5 份）→ 提示卡必然重新出现。
>
> 修复：把「哪些报告已经处理过」按文件名落盘（`logs/seen-crash.txt`），
> 提示卡只认**未处理**的报告。忽略旧报告后不再打扰；真出现新崩溃仍会提醒。

## 一、现场：把这条链走完

用户口中的「弹出」不是系统崩溃对话框，而是主屏顶部那张 `CrashNoticeCard`
（v1.6 加的「检测到 N 次闪退记录 / 发送日志 / 忽略」）。

| 环节 | 位置 | 实际行为 |
| --- | --- | --- |
| 报告怎么来的 | `AppLog.installCrashHandler()` | 未捕获异常时写 `filesDir/logs/crash-<时间>-<线程>.txt` |
| 最多留几份 | `AppLog.MAX_CRASH_FILES = 5` | 更早的自动删；**不会因「忽略」而删** |
| 卡片显示条件 | `ScanScreen.kt` | `crashReportCount > 0 && !crashNoticeDismissed` |
| 数量怎么算 | `ScanViewModel.refreshLogSummaryInternal()` | 每次都重新扫 `filesDir/logs/crash-*.txt` |
| 什么时候重算 | ViewModel init + 每次 `ON_RESUME` | 冷启动 / 回到前台都会算 |
| 点了忽略做什么 | `ScanViewModel.dismissCrashNotice()` | `crashNoticeDismissed = true`，**仅此一句** |

工程里没有任何 SharedPreferences / DataStore / 已读标记文件，`crashNoticeDismissed`
在 `ScanUiState` 里默认 `false`，而 `_uiState` 从创建后就没有整体重置的路径——
所以：

- **同一进程内**：点完忽略不会自己再弹（这条是符合预期的）；
- **进程重建后**：新 ViewModel → `false` → 磁盘上报告还在 → 又弹。

这就是「忽略了还一直弹」的完整闭环。而 v1.8.8 之前那段时间 App 确实还在频繁崩溃，
进程反复被拉起，于是用户看到的就是「怎么按都按不掉」。

## 二、为什么不选「点忽略就删报告」

最省事的改法是在 `dismissCrashNotice()` 里把 `crash-*.txt` 删掉——**不能这么做**：

> 这些文件是用户唯一能发回来的崩溃现场（堆栈 + 机型 + 崩溃前 200 行事件日志）。
> 「忽略」表达的是「这次先别打扰我」，不是「这些证据不要了」。
> 删掉之后用户再想反馈就没东西可发了，尤其我们是个不联网、不申请网络权限的应用。

所以证据和 UI 状态必须分开存：

| | 文件 | 谁来删 | 含义 |
| --- | --- | --- | --- |
| 崩溃报告 | `crash-*.txt` | 只由 `AppLog.clearAll()`（用户主动清空日志） | 证据 |
| 已读标记 | `seen-crash.txt` | 同上；也可单独 `clear()` | UI 状态 |

标记文件名**刻意以 `seen-` 开头**：如果叫 `crash-seen.txt`，就会被
`AppLog.crashReports()` 的前缀过滤当成一份崩溃报告统计进去，
出现「标记自己把自己触发成新报告」的死循环。

## 三、实现

### 新增 `logging/CrashNoticeStore.kt`

一个纯 JVM 类，只吃一个 `File dir`，不依赖 Android framework：

```kotlin
class CrashNoticeStore(private val dir: File) {
    fun unseen(reports: List<File>): List<File>   // 过滤掉已标记的报告
    fun markSeen(names: Collection<String>)       // 合并写入，不覆盖旧标记
    fun clear()                                   // 清掉标记
}
```

- 标记内容是**报告文件名**（文件名自带时间戳和线程名），一行一个；
- 写入走 tmp + rename：写到一半进程没了，最坏是旧标记还在（多提醒一次），不会读到半行；
- 最多保留 32 条，不让这个小文件无限增长（报告本身最多留 5 份）；
- 读写串行，避免 UI 线程读、IO 线程写时读到半状态。

**为什么不用 SharedPreferences / DataStore**：这个工程的 domain / data 层坚持纯 JVM 单测，
`SharedPreferences` 在 `app/src/test` 下会抛 "not mocked"。用文件还能真实测
「关掉实例、新建一个实例，状态还在」——那正是这个问题的核心场景。
与 `SessionStore` / `ScanHistoryStore` 的做法也一致。

### `AppLog` 增加两个查询口

```kotlin
fun unseenCrashReports(context: Context): List<File>
fun markCrashReportsSeen(context: Context, reports: List<File>)
```

`AppLog.summary()`（设置面板里那行「xx KB · 崩溃报告 N 份」）**保持原样**报总数——
那是事实陈述，不因为用户忽略了就假装日志没了。

### UI 状态拆成两个口径

这是这次修改里最容易改错的地方：

| 字段 | 含义 | 忽略之后 |
| --- | --- | --- |
| `crashReportCount` | 磁盘上报告总数，供设置面板提示与导出摘要用 | 仍然 > 0（证据还在） |
| `crashNoticeHandled`（新，替代 `crashNoticeDismissed`） | 是否还有**未处理**报告，决定提示卡显不显示 | true |

`refreshLogSummaryInternal()` 同时算这两个值；`dismissCrashNotice()` 和
`requestExportLogs()`（发送日志）都会把当前未读报告标记为已处理，然后立即重算状态。

于是三种情况都对：

1. 点忽略 → 标记落盘 → 本次和以后启动都不弹；
2. 真又崩了一次 → 产生新文件名报告 → 不在已读集合 → 照样弹；
3. 同一进程里又崩了一次 → `ON_RESUME` 重算 → `crashNoticeHandled = false` → 照样弹。

第 3 条顺便修掉了旧实现另一个方向的 bug：旧实现的布尔位一旦为 true，
**同一进程内再崩也不会提醒**——「一直弹」和「该弹不弹」其实是同一个设计缺陷的两面。

## 四、验证

新增 9 个纯 JVM 用例（`CrashNoticeStoreTest`，真临时目录、无 mock）：

| 用例 | 验证什么 |
| --- | --- |
| 无标记时全部未读 | 初始行为 |
| 标记后不再未读 | 基础语义 |
| 换实例仍记得 | **模拟进程重启**，用户报的问题本身 |
| 新报告仍会提醒 | 不被旧标记吞掉真崩溃 |
| 只标记一部分 | 部分处理 |
| 空行/垃圾行容错 | 标记文件被写坏时不会全盘误判 |
| 上限 32 条 | 文件不会无限增长 |
| 清空标记后恢复未读 | 与「清空日志」联动 |
| 标记文件名前缀不撞车 | 防止标记自己被当成崩溃报告 |

全量：**291 个用例，0 失败**（v1.8.9 的 282 + 新增 9）。

## 五、边界与未做的事

1. **标记按文件名，不按内容**。极端情况下（同一秒内同线程名崩溃、且旧报告已被
   `pruneOldReports` 清掉）新报告可能撞上已读文件名。实际需要 5 份报告在 1 秒内全部
   产生并重启进程才会发生，不值得为此改命名规则。
2. **「发送日志」也算处理过**。点击后就把报告标为已读——系统分享面板是否已把文件真正
   发出去，应用拿不到回调。用户取消分享也不会再被这张卡打扰；日志仍能在设置里重新发。
3. **没有设备可验**。本机 `adb devices` 为空，无法在真机上重现用户那台设备的弹窗顺序；
   本次修复基于完整的静态链路核查 + 9 个针对「跨实例」的单元测试。真机上若弹的其实是
   **系统级**的「应用已停止运行」对话框，那是仍在崩溃，需要新的崩溃报告，与本修复无关。
