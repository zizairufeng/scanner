## 2. 取证：预算本身算错了

这次没有凭直觉改代码。先用 `_height_audit.py` 按 Material3 默认排版逐项复算了
每一页的真实高度（不是估算总高，是逐个组件累加）：

参数：屏幕 420dp × 927dp（真机 1264×2780 @ density 3.0）；内容区宽 380dp；
RadioRow 内列 324dp；SwitchRow 内列 316dp；bodyLarge 16/24、titleSmall 14/20、
titleLarge 22/28、labelSmall 11/16；中文 1 字 = 字号 dp，英文/数字 0.55 折算。

复算结果（v1.4.3 当时的组件参数）：

| 页面 | 实际高度 | v1.4.3 预算 360dp | 溢出 |
|---|---|---|---|
| 扫码 | 513dp | 360dp | **+153** |
| 识别 | 498dp | 360dp | **+138** |
| 结果 | 389dp | 360dp | **+29** |
| 规则 | 324dp | 360dp | −36 |

四页里三页超出，最多 153dp。

内容区当时是 `Box(Modifier.weight(1f))` —— **既不裁剪也不滚动**。
多出来的 100 多 dp 无处可去，只能直接画在下面那条翻页按钮条上。
这就是用户看到的「元素重叠」：不是排版乱，是内容压到了翻页条上面。

### 为什么前三次都没发现

每次都是「改完就出包」，从没有一次把「这一页到底多高」算出来过。
高度是**拍脑袋定的常量**（360dp），而它要装的东西（副标题折行、
三个 radio 的档位说明、两个滑杆）从来没有人对过账。

## 3. 修法：双保险

### 3.1 预算 360dp → 520dp

依据不再是拍脑袋：

- 927dp 屏上 `ModalBottomSheet` 最大高度约 **90% = 834dp**；
- 扣掉固定开销 210dp → 内容最多能分到 **624dp**；
- 取 **520dp**，留 104dp 容错。

### 3.2 内容区改为「钉死高度内可滚动」

这是真正的保险，也是这次最重要的一条：

```kotlin
Column(
    modifier = Modifier
        .fillMaxWidth()
        .weight(1f)
        .padding(top = 4.dp)
        .verticalScroll(rememberScrollState())   // ← v1.4.4 新增
) {
    when (page) { ... }
}
```

以后预算再算错，后果也只是「滚动一下」，不会退化成重叠。
即：不再相信任何一次性的高度估算。

这里与 v1.4.1 那个**失败的** `verticalScroll` 有本质区别，别混淆：

| | v1.4.1 | v1.4.4 |
|---|---|---|
| 面板高度 | 不钉死（`heightIn(max)`） | **钉死**（固定 dp） |
| 滚动容器测得的父约束 | `infinity` | **确定值** |
| sheet 测量-摆放循环 | 按「内容无穷高」算，位置不可靠 → 仍撑满并裁掉 | 高度是常量，循环稳定 |
| 结果 | 失败 | 安全 |

v1.4.1 的问题不是「滚动」这个动作，而是在高度未确定的前提下滚动。

### 3.3 顺带做的三件事

1. 面板高度再跟屏高取一次 min —— 520 的预算是按 927dp 屏算的，
   小屏（如 800dp）上 sheet 自身可视上限更低，钉死 730dp 会被 sheet 从底部裁掉。
   注意取的是**屏幕高度**这个常量，不是内容高度，不会把测量循环带回坏前提。
   ```kotlin
   val screenLimitDp = LocalConfiguration.current.screenHeightDp * 0.9f
   val budgetDp = SettingsPage.PANEL_TOTAL_HEIGHT_DP.toFloat()
   val panelHeight = (if (budgetDp > screenLimitDp) screenLimitDp else budgetDp).dp + imeBottom
   ```

2. **去掉规则页自带的 `verticalScroll`** —— 两层竖向滚动容器嵌套时，
   外层会在 pre-scroll 阶段先吃掉滑动量，表现为「里面滚不动、外面滑一点」。
   单一滚动容器是唯一可控的写法。

3. **压缩组件**，让多数设备根本不需要滚：
   `SectionDivider` 上下 12 → 8dp（一页最多 4 条分隔线，这是主要开销）；
   `SwitchRow` / `RadioRow` 最小高 56 → 52dp、内边距 6 → 4dp；
   `StepSlider` 64 → 56dp；三条过长的 hint 各精简掉一句。

### 3.4 压缩后的复算结果

| 页面 | 压缩前 | 压缩后 | 预算 520dp | 余量 |
|---|---|---|---|---|
| 扫码 | 513 | **449** | 520 | −71 |
| 识别 | 498 | **410** | 520 | −110 |
| 结果 | 389 | **349** | 520 | −171 |
| 规则 | 324 | **316** | 520 | −204 |

四页全部落在预算内，最重的扫码页还余 71dp。
滚动是兜底，正常情况下用不到。

面板总高 = 210 + 520 = **730dp** ≤ 834dp（sheet 上限），放得下。

## 4. 测试

`SettingsPageTest` 从 11 条增至 **14 条**，新增/改写：

- `面板总高不超过sheet最大高度` —— 锁死 `PANEL_TOTAL_HEIGHT_DP ≤ SHEET_MAX_HEIGHT_DP`
- `内容预算大到能装下复算过的最重页面` —— 预算 ≥ 449dp（最重的扫码页）
- `预算给最重页面留出容错余量` —— 余量 ≥ 40dp，防止估算一偏就要滚
- `固定开销与预算之和与UI取的是同一处` —— 防止 UI 里再写一份硬编码脱节

这三条把「高度对账」制度化：以后改任何一个常量都会被拦住。

单测 127/127 通过（10 个套件）。

## 6. 经验

1. 「钉死高度」只解决了测量循环，没解决「装不装得下」。
   两个问题是独立的，v1.4.3 只解决了前者就以为完事了。

2. **`Box(weight(1f))` 不裁剪**。想让溢出可控，必须显式给
   `clip` 或 `verticalScroll`——默认行为是**直接画出去**。

3. 高度常量必须能追溯到逐项累加。写 360 的时候没有任何依据，
   写 520 的时候能拿出一张每页 449/410/349/316 的表。

4. **兜底优先于精确**。即使这次的 449 又算错了，滚动也会接住它。
   连续四轮失败的经验是：不要把正确性押在一次性估算上。
