# v1.8.7 — 点码复制失效：根因与修复

> 用户反馈：「点击码进行复制，无法复制，帮我检查一下，然后 review 一下代码。」
>
> 结论：不是剪贴板写不进去，是事件流被一具尸体卡住了。v1.8.6 删掉
> `SnackbarHost` 之后，`SnackbarHostState.showSnackbar` 变成了永久挂起，
> 于是第一次点复制之后，整个 `events.collect` 协程再也没往下走过一行。

## 一、根因（P0）

### 现场

`ScanScreen.kt` v1.8.6 的写法：

```kotlin
// 事件消费
LaunchedEffect(Unit) {
    viewModel.events.collect { event ->
        is UiEvent.CopyToClipboard -> {
            val ok = context.copyToClipboard(event.text)   // ← 剪贴板其实写进去了
            snackbarHostState.showSnackbar(message)         // ← 卡在这里，永不返回
        }
        ...
    }
}

// 状态栏渲染
statusBar = {
    val bar = snackbarHostState.currentSnackbarData   // 自己读出来画
    ...
}
```

**没有 `SnackbarHost` 这个 Composable。**

### Material 3 的契约

`androidx.compose.material3.SnackbarHostState` 的实现（官方 android/androidx 源码）：

```kotlin
public suspend fun showSnackbar(visuals: SnackbarVisuals): SnackbarResult = mutex.withLock {
    try {
        return suspendCancellableCoroutine { continuation ->
            currentSnackbarData = SnackbarDataImpl(visuals, continuation)
        }
    } finally {
        currentSnackbarData = null
    }
}
```

它是 `suspendCancellableCoroutine`——**只有 `dismiss` 或 `performAction` 才会让它恢复**。
而这两个方法唯一的调用者是 `SnackbarHost` 里的定时器：

```kotlin
@Composable
public fun SnackbarHost(hostState: SnackbarHostState, ...) {
    val currentSnackbarData = hostState.currentSnackbarData
    LaunchedEffect(currentSnackbarData) {
        if (currentSnackbarData != null) {
            delay(duration)
            currentSnackbarData.dismiss()      // ← 到点儿消失，全靠这一行
        }
    }
    FadeInFadeOutWithScale(...)
}
```

**`currentSnackbarData` 是 public 的读接口，但「到期消失」这个行为长在 `SnackbarHost` 身上。**
v1.8.6 只借用了前者、扔掉了后者，`SnackbarHostState` 就退化成一个永不超时的消息槽。

### 因果链

```
第一次点复制
  └─ copyToClipboard() 成功，剪贴板里确实有值
  └─ showSnackbar() 挂起 → events.collect 这条协程停在这一帧
      ├─ 之后点任何一条码：事件只进 16 槽缓冲，没人消费 → 复制没发生
      ├─ 撤销 / 导出 / 设置回执：同样没人消费 → 全静默
      └─ 状态栏：snackbar 分支优先级最高且永远清不掉
                 → 永久停在「已复制该条码值」，之后所有扫码反馈都被它压着
```

这解释了用户看到的现象「第一次好像还行，之后就点不动了」。也解释了为什么
这一版**其他提示全都失灵**——它们和复制共用同一条被堵死的事件流。

### 为什么之前没发现

v1.8.4 / v1.8.5 里 `TopSnackbarHost` 是渲染了一个真正的 `SnackbarHost` 的，
只是把它塞进了顶部槽。v1.8.6 为了「画面里什么都不放」，把那个 Composable 一并删了，
改成读 `currentSnackbarData` 自己画——这一步在编译、单测、静态检查里都完全静默。
`SnackbarHostState` 的公开 API 只有读接口，误用在类型上是合法的。

## 二、修复

### 1）不再使用 `SnackbarHostState`

状态栏本来就是自己画的，没必要借 Material 的壳。改成自己持有状态 + 显式定时器：

```kotlin
internal data class Notice(
    val id: Int,                 // 自增序号：让连续两条相同文案也能重新计时
    val text: String,
    val tone: HintTone,
    val actionLabel: String? = null,
    val onAction: (() -> Unit)? = null
)

var notice by remember { mutableStateOf<Notice?>(null) }
var undoNotice by remember { mutableStateOf<Notice?>(null) }   // 撤销单独一槽

LaunchedEffect(notice?.id) {
    val current = notice ?: return@LaunchedEffect
    delay(if (current.tone == HintTone.ACTION) ACTION_MS else INFO_MS)
    if (notice?.id == current.id) notice = null
}

LaunchedEffect(undoNotice?.id) {
    val current = undoNotice ?: return@LaunchedEffect
    delay(ScanHintSpec.UNDO_MS)
    if (undoNotice?.id == current.id) { undoNotice = null; viewModel.dismissUndo() }
}
```

三条关键点：

- **`if (notice?.id == current.id)`**：定时器醒来时不盲目清空。期间若来了新通知，
  id 已变，旧定时器直接放弃——否则第二条通知会被第一条的定时器提前掐掉。
- **撤销独立一槽**：`statusOf` 里它排第一。这样复制一条码不会把撤销按钮顶掉，
  而 v1.8.6 之前用 Snackbar 队列时是「排队等前一条消失」，反而更差。
- **撤销过期才 `dismissUndo`**：按钮可见 ⇔ 快照有效，这两件事现在严格同步。

### 2）事件处理器加异常隔离

```kotlin
viewModel.events.collect { event ->
    try { when (event) { ... } }
    catch (t: Throwable) { AppLog.e(TAG, "处理界面事件失败：$event", t) }
}
```

原来任何一条事件抛异常，都会连带取消整个收集协程 → 后面所有提示静默失效，
症状和这次的 bug 一模一样（「按了没反应」），极难查。现在单条失败只丢这一条。

### 3）格式名随事件下发

`UiEvent.CopyToClipboard` 新增 `formatLabel`。原来 UI 在消费事件时现读
`uiState.copyFormat`——用户在「复制」到「消费事件」之间改了格式，提示语会写出一个
**并没有真的用到**的格式名。事件是自己那一刻的事实，就该随身带着。

### 4）`UNDO_MS = 4000` 进规范

撤销窗口以前借用 `SnackbarDuration.Short`（4 秒），现在显式定义在 `ScanHintSpec`，
并由测试锁死 4000。它同时是删除快照的有效期，两边必须同步。

## 四、验收

- 单测 **255/255**（v1.8.6 是 253，新增 2 条：撤销压过回执、撤销按钮必须带回调；
  改 1 条：时长档位从两档改为三档）

- 权限仍只有 `CAMERA` + `VIBRATE`
- 新增护栏：`ScanHintSpecTest` 锁死 `UNDO_MS == 4000`；
  `StatusPriorityTest` 锁死「撤销 > 通知 > 重复码 > 失焦 > 回执 > 引导 > 诊断」

## 五、留给下个版本的教训

不要借用一个组件的「状态」，却扔掉驱动它的那个组件。

`SnackbarHostState.currentSnackbarData` 看起来是个普通状态，读它就能渲染；
但它的写入方（定时器）在 `SnackbarHost` 里。这类「状态 + 隐藏驱动者」的组合，
误用在类型系统里零告警，只能靠知道实现细节来避免。更稳的做法是：
要自己画，就连状态一起自己持有——反正最终像素是自己排的。
