# v1.8.9 — 扫描历史账本：每一次扫码都实时落盘

> 用户需求：「增加一个功能，把每次扫描出来的数据都保存下来，方便搜索。能实现同步保存。不丢失。」
>
> 这句话里有三个明确约束，任何一个做松了都算没做：
>
> 1. **每一次** —— 不是「当前列表」的镜像，是**所有**扫到过的事件；
> 2. **方便搜索** —— 要能按码值片段查，不是只能从头翻；
> 3. **同步保存、不丢失** —— 扫码那一刻就落盘。进程被杀、闪退、直接断电，都不能丢。
>
> 做法：新增一份**独立的追加式账本** `ScanHistoryStore`，按天分片、逐批 `fsync`，
> 与「会话快照」彻底分开。新增 25 个纯 JVM 用例，全量 282 个用例通过。

## 一、为什么不复用 `SessionStore`

工程里原本就有一个 `SessionStore`（会话快照，用来实现「切走再回来列表还在」）。
直觉上把历史塞进去最省事，但它是**反面**的：

| | `SessionStore` | `ScanHistoryStore`（新） |
| --- | --- | --- |
| 回答什么问题 | 这次盘点**还剩**什么 | 这台机器**扫到过**什么 |
| 写入方式 | 整文件覆盖（写 tmp → rename） | 末尾追加 |
| 删除时机 | 用户清空列表 / 丢弃会话 / 列表变空 | **只有**用户主动清空历史 |
| 数据规模 | 一个会话（几十 ~ 几千条） | 无限（按天分片） |

关键在第三行：「清空列表」是扫码过程中的**高频动作**（换一批货就清一次）。
一旦两者共用一份文件，清空列表就会顺手把账本一起清掉——那恰恰是用户要避免的事。
所以这一个功能的支点就是**分成两份**，不是一个可选项。

## 二、为什么是「追加 + 每天一个文件」

### 崩溃安全模型（决定性理由）

| 方案 | 写到一半进程被杀 | 断电 |
| --- | --- | --- |
| 整文件重写（tmp + rename） | 旧文件还在，但**这次的新数据全丢** | 同左 |
| 追加写（本方案） | 最后一行可能不完整（解码判坏行丢弃），**前面几千行完好** | 已 `fsync` 的部分全在 |

追加写只有「写完 / 没写完」两种状态，没有「文件处于半新半旧」的中间态。
这与用户「不丢失」的要求是直接对应的——不是理论上的优雅，是唯一能兑现承诺的写法。

### 其他两个理由

- **搜索有边界**：查「今天」只读今天那一个文件，不会因为攒了三个月的历史而变慢；
- **不引依赖**：这个工程的 release 构建是离线的（`--offline`），Room + KSP 的构建期
  产物根本拉不下来；而直接上 SQLite 会把这块逻辑变成「只能在真机上验」的黑盒，
  违背本项目「domain / data 层用纯 JVM 单测覆盖」的做法。

## 三、实现

### 分层

```
domain/
  ScanRecord.kt    一条历史事件（时间 / 类型 / 码制 / 码值 / 会话 / 来源）
  HistoryCodec.kt  行编解码（decode 不抛异常，一行坏掉不影响同文件其余几千行）
  HistoryQuery.kt  匹配口径 + 时间范围（纯逻辑，可单测）
  TsvCodec.kt      转义规则（从 SessionStore 抽出，两边共用，保证逐字节兼容）
data/
  ScanHistoryStore.kt   追加式账本：写线程 / 分片 / 搜索 / 统计
ui/
  HistoryViewModel.kt   搜索状态 + 120ms 防抖
  components/HistorySheet.kt   弹层（搜索框 + 时间 chips + 结果列表 + 导出/清空）
```

### 写路径：识别回调只负责入队

```
识别回调（20fps）
   └─ recordHistory() → history.append(records)      ← 只入队，微秒级
                            ↓ 无界 LinkedBlockingQueue
写线程 "scan-history"（守护线程）
   └─ 合并连续 Append → 逐条 write → fd.sync()        ← 落盘后才算成功
```

三处刻意的选择：

1. **写盘在独立线程**，不在识别回调上。把 `fsync` 搬到识别线程会让每帧多一次 IO 抖动，
   20fps 的识别循环会明显掉帧。
2. **队列无界**。v1.8.8 那次闪退的根因就是向已关闭的线程池投任务被 `AbortPolicy` 拒绝
   （见 `27-v1.8.8-相机闪退修复.md`）。有界队列 + 拒绝策略是同一个坑，不再踩第二次。
   代价是磁盘彻底写不进去时队列会涨——但那种情况 `onError` 已经报出来了，不会假装在保存。
3. **每批写完 `fd.sync()`**。不是依赖 OS 刷盘：只有 `fsync` 返回之后才认为这条记录安全。

连扫时一帧一个任务，所以写线程会把**连续的 `Append` 合并成一批**，一次 `write` +
一次 `fsync` 全部搞定，避免 `fsync` 成为瓶颈。

### `flush()` 是 FIFO 屏障

`flush()` 往同一个队列里投一个带 `CountDownLatch` 的任务。队列是 FIFO 的，
所以它被执行时，**它之前的所有 append 一定已经写完并 sync 过**。

调用点有三处：

| 时机 | 调用 | 目的 |
| --- | --- | --- |
| 切后台（`ON_STOP`） | `flushPersist()` | 用户扫完直接按 Home / 锁屏也不丢 |
| ViewModel 销毁 | `onCleared()` 里 `flush(500)` | 退到桌面、换设备前最后补写一次 |
| 打开历史面板 | `search()` 内部先 `flush()` | 刚扫完就点历史，不该看不到最后几条 |

注意 `flushPersist()` 里历史刷盘**放在 `persistEnabled` 判断之前**：那个开关管的是
「会话快照要不要留」，关掉会话保存不该连带停掉历史。

### 清空必须经过写线程

`clear()` 也是一个队列任务，而不是直接 `File.delete()`。原因：

> 正在被追加的那个分片如果被直接删掉，**打开着的 fd 会继续往一个已经不在目录里的
> inode 写入**。表现是「清空之后空间没释放，而且再也找不到这些数据」。
> 必须先 `closeStream()` 再删文件，顺序不能换。

### 记哪三类事件

严格去重 / 计数聚合 / 允许重复是三种口径，屏幕上能不能看到反应差别很大，所以历史分开记：

| 类型 | 什么时候 | 屏幕上 |
| --- | --- | --- |
| `NEW` | 新增了一行 | 列表多一条 |
| `INC` | 计数聚合下给已有行 +1 | 行数不变、数量 +1 |
| `DUP` | 严格去重下被丢弃的重复码 | **什么都没有**（可能只闪一下提示） |

`DUP` 是这一层最容易被忽略、也最有用的部分：现场经常是「这个码我刚才到底扫过没有」，
而屏幕上什么都不留。只有历史能回答。

一个细节：计数聚合模式下，同一个码在同一帧里**既是 `INC` 又是 `DUP`**
（`CodeAdmission` 两处都加了）。如果分别记账，「这台机器上这个码扫过几次」会虚高一倍。
所以先算 `increments` 集合，再从 `duplicates` 里排掉。

`INC` / `DUP` 在准入结果里只有码值、没有码制，写历史时从当前列表反查一次。
反查是 O(列表长度) 的线性扫描，但在人类的扫码节奏下每帧最多发生个位数次；
而为此维护全量索引反而要在每次删除时都跟着维护。

### 搜索：从最新的分片往前读

```
分片倒序（scans-2026-11-12.tsv 在前）
   └─ 读一天的记录 → 文件内时间递增，倒着取
        └─ 凑够 limit + 1 条就停 → 截断标记
```

所以「最近的事」永远最先返回，老数据再多也不拖慢常用查询。
匹配口径定了三条：

- **子串匹配、忽略大小写**。现场输入的是码的一部分（只记得后六位、只记得批次号），
  子串才是能用的口径；
- **空格分隔多个词 = 全部包含（AND）**。`6901 0215` 只命中同时含这两段的码值；
- **只在码值上匹配，不在码制名上匹配**。用户搜 `EAN` 想找的是条码内容，
  而所有 EAN-13 的 `formatName` 都命中会给他一堆并不是要找的东西。

### 界面

右上角新增「历史」按钮（在「相册」之前），点开是浮层而不是新页面——
和设置 / 相册 / 导出同一个理由：**不跳页就不会销毁相机**，关掉浮层立刻能接着扫。

浮层内容：搜索框、时间范围 chips（今天 / 7 天 / 30 天 / 全部）、「本次运行」开关、
顶部统计（多少天 · 多少条 · 占多大）、结果列表、「导出这些」/「清空」（二次确认）。

时间范围按**自然日**算而不是「now − 7×86400_000」：

> 盘点是按天对账的。用户说「7 天」指的是 7 个日历日；滚动 168 小时会把
> 「上周同一天早上」切掉一半。

导出复用结果导出那条分享通路，三种格式列是 `时间 / 类型 / 码制 / 内容 / 来源`；
CSV 带 UTF-8 BOM（Excel 直接双击不乱码），XLSX 的 sheet 名「扫描历史」。

## 四、唯一会丢的窗口，以及为什么不消掉它

`append()` 入队之后、写线程真正执行之前，有一个**通常 < 5ms** 的窗口。
这个窗口里进程被杀，这几条就没了。

要彻底消掉只能把写盘（含 `fsync`）搬到识别回调线程上，代价是每帧多一次同步 IO——
对 20fps 的识别循环不可接受。权衡后保留这 5ms，并在 `ScanHistoryStore` 的 KDoc 里
写清楚，不假装它是零。

对比一下：用户担心的「闪退丢数据」通常是「扫了半小时，退出时崩了，全没了」这种量级。
5ms 窗口最坏丢的是**最后那一两个码**，而且是它们还停在内存里的那一瞬间。

## 六、已知的边界与后续可做

1. **历史没有容量上限**。一条记录约 60~80 字节（EAN-13），
   十万条约 7MB、一年的高频使用也在几十 MB 量级。目前不做自动清理——
   用户要求的是「不丢失」，静默删老数据违背这个承诺。如果将来要加，
   应该是「提示用户后按时间清理」，而不是自动滚动的环形缓冲。
2. **历史保存开关不跨进程保留**。与工程里其它设置项（震动、提示音、会话保存）
   一致，重启回默认值 `true`。要做的话需要新增一个设置存储，属于独立改动。
3. **没有按码制筛选**。搜索只按码值。加一个码制下拉是容易的，
   但现在的界面已经有三行控件，再塞会挤。
4. **`HistoryRange.isBounded` 已预留**，用于「结果按天分组显示」的日期吸顶头，尚未实现。
5. **统计（`stats()`）会读全部分片**，所以带缓存、只在打开面板和清空之后算。
   如果历史涨到几十万条，这里会变成打开面板时的卡顿点，届时应改为
   「按分片缓存条数、只累加变化的分片」。
