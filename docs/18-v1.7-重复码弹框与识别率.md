# v1.7：重复码弹框提醒 + 小码识别率提升

> 版本 **1.7.0（versionCode 12）**，2026-11-03。
> 这一版只有两个主题，都是用户直接提出来的：
> ①「扫到重复码要弹框提醒」；②「这个码（硬盘标签上的小 Data Matrix）识别率有点低」。

---

## 0. 结论先说

| 问题 | 做法 | 效果 |
|---|---|---|
| 重复码没有任何反馈 | `DuplicateMonitor` + `DuplicateAlert` + 弹框 + 两下短震 | 用户能立刻分清「已扫过」和「没识别出来」 |
| 小码/细密 Data Matrix 解不出 | 中心区放大补扫 + 对比度拉伸二次尝试 + ZXing 第二引擎 + 点击对焦 + 失焦提示 | 管线从「1 次全帧识别」变成「4 级兜底」，见 §2 |
| 手机会不会因此变卡 | 所有兜底都只在**全帧一码未解**时才走；单次精读超过 150ms 就放弃后续尝试 | 正常扫码快路径一行没改 |

203 个单元测试全绿（v1.6 是 165 个），`assembleDebug` / `assembleRelease` 均通过，
release 已签名对齐并发布到下载页。

## 1. 重复码弹框

### 1.1 它到底修的是什么

严格去重模式下，重复码在 `CodeAdmission` 里是被**静默丢弃**的：
`admission.isEmpty()` → 直接 `return`，不震动、不闪边框、不写日志。

用户看到的现象是「手机对着码，屏幕毫无反应」，于是开始凑近、晃动、换角度——
而他真正需要知道的只是「这个已经扫过了，在第 3 行」。

### 1.2 数据流

```
BarcodeAnalyzer ──codes──▶ ScanViewModel.onCodesDetected
                              │
                    校验位 → 准入规则 → CodeAdmission
                                            │
                            AdmissionResult(newCodes, increments, duplicates)   ← v1.7 新增 duplicates
                                            │
                        DuplicateMonitor.recordAndShouldAlert(value, now)
                                            │  两级冷却
                                    DuplicateAlert → UiState → AlertDialog
```

`AdmissionResult` 新增 `duplicates` 字段（默认空列表，既有构造点零改动）。
三种口径语义不同，必须分开：

| 口径 | 会不会计入 | 是否上报 duplicates | 弹框说什么 |
|---|---|---|---|
| 严格去重 | 否 | 是 | 「本次未计入」 |
| 计数聚合 | 数量 +1 | 是 | 「已累加到 ×N」 |
| 允许重复 | 每次新增一行 | **否** | —（这种模式里每个码都是新记录，弹框是纯噪音） |

### 1.3 为什么必须节流

`DedupeTracker` 只保证「同一秒内不重复上报」。用户如果把手机一直对着同一个码，
每过一个时间窗（默认 1.5s）就会再来一次重复判定——**每 1.5 秒弹一次窗是不能用的**。

于是 `DuplicateMonitor` 做两级冷却：

- **单码冷却 3s**：同一个码两次弹框至少隔 3 秒；
- **全局冷却 1.2s**：任意两次弹框至少隔 1.2 秒（货架上一排同款被逐个扫过时有用）。

关键细节：**无论弹不弹，命中次数都累加**。否则「第 N 次扫到」会说错。
`hitsOf()` 只统计重复命中，所以 UI 上显示的是 `hits + 1`（含第一次扫码）。

### 1.4 UI 取舍

- 用 `Dialog` 而不是 Snackbar：这个信息要求用户**看清码值**再决定下一步，
  Snackbar 一闪而过，还会被扫下一件的动作顶掉。
- **只有一个按钮「知道了」**：连扫场景里任何需要精确点击的二次选择都会打断节奏；
  删除/跳转在列表里本来就能做。
- 6 秒自动消失：连扫时用户多半不会去点按钮。
- 弹框不暂停相机：相机与分析器仍在跑，扫到别的码照常计入。
- 已有弹框时**不覆盖**：用户正在读的那条信息不该被下一帧顶掉。
- 反馈是**两下短震、不出声**（`FeedbackPlayer.playDuplicate`）：
  「成功」和「重复」两声提示音调子太接近，靠听分不清；「两下」这个节奏可辨认。
- 开关在「设置 → 结果 → 重复码弹框提醒」，默认开启。

## 2. 识别率：这次加了什么、凭什么

### 2.1 先把「为什么解不出」拆开

调研（来源见 §5）后，小码解不出只有四类原因，而**算法只占其中一小部分**：

| 原因 | 现象 | 这次的处理 |
|---|---|---|
| ① 码在画面里占的像素太少 | 远距 / 小码 | 中心区放大补扫（§2.2） |
| ② 码没压住画面中心 | **Data Matrix 特有**：连候选框都不会有 | 中心区补扫 + 取景框提示（§2.2） |
| ③ 对比度不足 / 反光 | 灰阶被压在 90~150 一小段 | 对比度拉伸后二次识别（§2.3） |
| ④ 失焦 | 手机贴得太近（10cm 内根本对不上焦） | 点击对焦 + 「太近会失焦」提示（§2.4） |

ML Kit 官方文档里有两条硬约束，这一版就是围绕它们做的：

> - *the smallest meaningful unit of the barcode should be at least 2 pixels wide…*
>   *in applications where latency is critical, you can improve performance by capturing images
>   at a lower resolution, **but requiring that the barcode make up the majority of the input image**.*
> - *For a Data Matrix code to be recognized, **the code must intersect the center point of the input image**.
>   Consequently, only one Data Matrix code can be recognized in an image.*

第二条是本版的关键发现。**在这之前，凡是「Data Matrix 偏在画面边角」的情况，
`RoiPlanner` 那条路根本不会被触发**——因为它依赖「粗检出候选框」，
而没有候选框就没有 ROI，于是什么都不会发生。

### 2.2 中心区放大补扫（`RoiPlanner.centerPlan`）

全帧解不出、候选框精读也没结果时，裁出画面中央 60%：

```
720p 全帧 1280×720
  └─ 中央 60%：768×432（码在其中的占比 ×1.67）
       └─ 放大到长边 1200（≤2×，不硬插值出假高清）
            └─ ML Kit → 失败则 ZXing
```

两个作用：① 码落在**新的**图像中心上，满足 Data Matrix 的硬约束；
② 码占画面比例大幅上升，满足「条码应占据输入图的大部分」。

按 250ms 节流（对着空白区域持续失败时不必每帧重解同一块），并带完整单测
（4 个旋转角、比例夹取、非法输入，见 `RoiPlannerCenterTest`）。

### 2.3 对比度拉伸 + 第二引擎（`ImageEnhance` / `ZxingDecoder`）

候选框精读第一次失败后，再做一次「拉伸 + 放大 + 双引擎」：

- `ImageEnhance.contrastStretchInPlace`：按 2% / 98% 分位把灰阶线性拉到 0~255。
  是 CLAHE 的极简替代——不分块、不插值，一次遍历。它**不创造细节**，
  也救不了强反光把码吃掉的那一块，所以只在第二次尝试时用。
- `ZxingDecoder`：ZXing core 是纯 Java 传统算法（定位图案 + 自适应二值化 + RS 纠错），
  失败模式和 ML Kit 的 CNN **不重叠**——它不要求码在画面中心，但要像素够、对比度够。

**一个被实测逼出来的修正（重要）**：ZXing 的 DataMatrix 检测依赖**静区**。
用 ZXing 自己的 `DataMatrixWriter` 编一张码再喂回自己的 reader，
不加白边是 `NotFoundException`，**补 4px 白边立刻就解出来**。
所以 `decode()` 现在会先四周补一圈白边（短边的 6%，夹在 6~48px），
对应真实场景就是「ROI 裁得太紧、静区被切掉」。这条已固化成单测。

### 2.4 对焦：这是算法救不了的部分

调研到的物理事实：**手机镜头最近对焦距离普遍 10~12cm**（无微距镜头的机型）。
而硬盘标签上那颗码只有约 5mm，用户本能地会贴近到 5~8cm——那个距离物理上就是糊的。

所以做了两件事：

1. **单击预览对焦**（`FocusMeteringAction` + `PreviewView.meteringPointFactory`），
   锁定 3 秒后自动回到连续对焦。用 PreviewView 自己的工厂而不是手算传感器坐标，
   是这类代码最常见的错（横竖屏切换后对焦点会偏）。
2. **失焦提示**：连续 12 帧「有候选框但一码未解」时，弹一条
   「太近会失焦：退到 15cm 左右，点屏幕对焦」，15 秒冷却。
   正向提示比让用户继续猜有用得多。

### 2.5 一条被放弃的尝试

`AnalysisProfile.DEFAULT` 保持 720p **没有改**。理由：改大会让所有用户的耗电无声上升，
而 v1.7 的兜底管线已经能在 720p 下拿到「把中央那块放大到 1200 长边」的效果。
需要更高上限的用户仍可自己选 1080p / 1440p 或打开「增强识别」。

### 验证边界（诚实版）

编译、单测、签名、dex 抽查能证明**代码在包里、纯逻辑正确**，但证明不了：

- 弹框在真机上的实际观感（会不会挡住取景框、6 秒是否合适）；
- 中心区补扫对**具体那台手机 + 那张标签**的实际提升（需要现场扫几十次统计）；
- 点击对焦在具体机型上的行为（不同厂商 AF 实现差异很大）。

这三项需要用真机实测，`adb devices` 当前为空，未做。

## 4. 给用户的使用建议（比任何算法都有效）

扫硬盘标签上这种 5mm 的细密 Data Matrix：

1. **不要贴到 10cm 以内**——退到 15cm 左右，用 2× 变焦放大（双击画面切换）；
2. **把码放在取景框正中央**——Data Matrix 必须压住画面中心才会被识别，偏一点就永远解不出；
3. 轻点画面把焦点对到标签上，等它「咬」住再稳 0.3 秒；
4. 标签有反光时**稍微偏一下角度**（斜着看），让反光点移开码面；
5. 还是解不出就看清单上印的 S/N 手动补一条——比跟一颗码僵持更划算。

## 6. 仍然没做的

| 候选 | 为什么先不做 |
|---|---|
| 多帧投票（同码连续 2~3 帧一致才采纳） | 能降误识，但与「连续快扫」的手感冲突，得先有真机数据决定窗口长度 |
| CLAHE 分块增强 | 现在这版全局拉伸已覆盖大部分反光场景；分块要处理块边界插值，收益未验证前不值得加复杂度 |
| OpenCV WeChatQRCode | 只支持 QR、+20~30MB/ABI、需 NDK（这块逻辑就没法单测了），而用户这次遇到的是 Data Matrix |
| 常开微距 AF 模式（`CONTROL_AF_MODE_MACRO`） | 部分机型不支持该模式，需要先探测 `CONTROL_AF_AVAILABLE_MODES`；点击对焦 + 距离提示已能覆盖主要场景 |
