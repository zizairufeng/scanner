## 0. 结论先说

**换库不是答案。** ML Kit 17.3.0 已经是最新的打包版本，在「免费 + 完全离线 + 无授权费」
这个约束下没有更强的替代者；比它强的（Dynamsoft / Scandit）是商业授权，且需要联网激活或付费。

真正的提升空间在**管线设计**，而且有两个改动是**零依赖、可单测**的，完全符合本项目
「`v4engine/` `v4web/` 只准标准库」那条红线：

| 优先级 | 措施 | 对症 | 代价 | 可验证性 |
|---|---|---|---|---|
| **P0** | **ROI 二次精读**（低分辨率粗检 → 裁候选框 → 放大再解一次） | 小码、远距码 | 一次 Bitmap 裁剪，开销远低于抬全帧分辨率 | 全部为纯逻辑，可 JVM 单测 |
| **P0** | **校验位自校验**（EAN-13 / UPC-A / Code-128 mod-10/103） | 误识（准确率） | 纯算术 | 纯函数，可单测 |
| P1 | CLAHE 局部对比度增强 + 轻锐化（只在 ROI 上做） | 暗光、塑料膜反光、轻微失焦 | 一次像素遍历 | 可单测（输入 Bitmap 输出统计量） |
| P1 | 多帧投票（同码连续 2~3 帧一致才采纳） | 抖动、运动模糊、误识 | 需要帧缓存 | 可单测（状态机） |
| — | 换 / 加引擎 | — | 见第 3 节 | — |

## 1. 现状盘点：我们已经做了什么

调研前先把家底摸清楚，避免重复建设。**已具备**：

| 能力 | 位置 | 说明 |
|---|---|---|
| 官方 autozoom | `camera/BarcodeFormats.kt` `createScanner(onZoomSuggested=...)` | v1.4 已接 `ZoomSuggestionOptions` |
| 码制白名单 | 同上，显式 7 种 | 刻意不用 `FORMAT_ALL_FORMATS`，避免货架文字被误判成 Code-39 |
| 潜在条码 | 同上 `enableAllPotentialBarcodes()` | 拿到「有码但没解开」的候选框 |
| 三档分析分辨率 | `domain/ScanTuning.kt` 1280×720 / 1920×1080 / 2560×1440 | 对应 1.0× / 2.25× / 4.0× 像素密度 |
| 帧间隔节流 | `camera/BarcodeAnalyzer.kt` `@Volatile frameIntervalMs` | 省电降温 |

### 1.1 一个容易踩的坑，我们恰好避开了

ML Kit 官方的 autozoom 有个**已知失效场景**：如果使用 `MlKitAnalyzer`
（CameraX 提供的预制 `ImageAnalysis.Analyzer`），`ZoomCallback` **永远不会被调用**。

原因（StackOverflow 上有人扒过）：`MlKitAnalyzer` 接受的是 `List<Detector<?>>`，
泛型擦除后内部统一走
`Detector.process(image: Image, rotation: Int, transform: Matrix)` 这条泛化路径，
而 `ZoomSuggestionOptions` 只在
`Detector.process(image: InputImage)` 这条路径上被处理。
`MlKitAnalyzer` 是 `final` 的、内部方法私有，无法覆写，只能复制源码改写。

**我们的 `BarcodeAnalyzer` 是自己写的，直接调 `scanner.process(inputImage)`**
（`BarcodeAnalyzer.kt:86`）——走的是正确的那条路。
所以 v1.4 接的 autozoom 是**真的生效**的，不是摆设。这一点值得记一笔，
后期如果谁想把 `BarcodeAnalyzer` 换成 `MlKitAnalyzer`「简化代码」，
会**静默**把 autozoom 干掉。

## 2. ML Kit 的硬指标（官方文档，可当常量用）

ML Kit 对输入图像有明确的像素要求，这是设计 ROI 逻辑的依据：

| 码制 | 最小单位 | 整码最小宽度 | 依据 |
|---|---|---|---|
| 通用 1D | ≥ **2 px** 宽 | — | 条/空的最小单元 |
| 通用 2D | ≥ **2 px** 宽×高 | — | 模块最小单元 |
| **EAN-13** | 1/2/3/4 单位宽 → 2/4/6/8 px | **≥ 190 px** | 整码 95 单位 × 2px |
| **PDF417** | 17 单位/word | **≥ 1156 px** | 每行最多 34 words |

官方推荐分辨率：**1280×720 或 1920×1080**，兼顾距离与延迟。

> 行业实践里更严：微小码要求模块 **≥ 3–4 px** 才稳（见第 6 节参考资料）。

### 2.1 这条指标直接解释了「小码解不出」

举例：1080p（1920×1080）全帧里，一个 EAN-13 只占画面宽度 10%，即 192 px —— 刚好压线。
再远一点占 5%，只剩 96 px —— **不足 190 px 的一半，ML Kit 必然解不出**。

要救它，全帧就得提到 3840 px 以上。**但同样的效果，把那一小块裁出来放大 2 倍就够了**，
而且解码器处理的像素量只有全帧的几十分之一。这就是 P0 的核心。

## 3. 候选引擎横向对比

| 方案 | 授权 | 支持码制 | 对小码/复杂码 | 体积代价 | 结论 |
|---|---|---|---|---|---|
| **ML Kit 17.3.0**（现用） | 免费 | 1D + 2D 主流 13 种 | 中等，依赖像素密度 | 已含 | **保持** |
| **OpenCV `wechat_qrcode`** | 开源（Apache 2.0） | **仅 QR** | **强**（CNN 检测 + 超分辨率重建） | OpenCV + 模型，**约 20–30 MB/ABI** | 备选，见下 |
| **zxing-cpp** | 开源（Apache 2.0） | 1D + 2D 20+ 种 | 1D 上可能强于 ML Kit，纯 C++ 无依赖 | 小（~1 MB/ABI） | 可作**补充解码器** |
| ZXing (Java) | 开源 | 多 | 弱（老算法，对模糊/畸变差） | 小 | 不建议 |
| ZBar | 开源 | 1D 为主 | 弱，QR 支持差 | 小 | 不建议 |
| Dynamsoft Barcode Reader | **商业** | 全 | 很强 | 授权 + 体积 | 不符合项目性质 |
| Scandit | **商业** | 40+ | 最强（宣称 >99%，0% 误识） | 授权费 + 需激活 | 不符合项目性质 |

### 3.1 关于 WeChatQRCode 的现实评估

它的技术路线确实对症：**Caffe CNN 检测器定位 → 对小/模糊码做超分辨率重建 → 解码**，
三级流水线，微信多年调优。对「**复杂二维码**」这个用户明确提过的诉求，它是目前
开源方案里最强的。

但三个硬约束让它**不适合作为主引擎**：

1. **只支持 QR Code**。盘点是 EAN-13 / Code-128 / Data Matrix 混扫，换成它等于丢掉 1D。
2. **体积**：需要完整 OpenCV + 4 个 ABI 的 so + 模型文件。当前 release 包 11 MB，
   引入后可能翻倍到 25–35 MB。对一个内网分发的工具 App 是明显的退化。
3. **工程量**：需要 NDK 构建、JNI 封装，与项目「纯 Kotlin + 可 JVM 单测」的架构冲突——
   这块逻辑将**无法单测**。

> ⚠️ 网上（CSDN / GitCode 等）流传的 WeChatQRCode 性能数字（「98.7% 识别率」
> 「50ms」「比 ZXing 快 300%」）**来源不可靠**，多为项目推广稿件，且对比基线不明确。
> 真要用必须自己造测试集实测，不能采信这些数字。

**结论：不建议换。** 若将来「复杂二维码」成为主要痛点，可考虑把 WeChatQRCode 做成
「QR 专用增强通道」——仅在 ML Kit 对某个 QR 候选连续失败 N 帧后，对这一小块 ROI 调用，
而不是全帧走两套引擎。这样体积和性能都可控。**但这是后话，优先级低于 P0。**

## 4. P0-1：ROI 二次精读（推荐）

### 4.1 思路

现在是**单段管线**：

```
全帧（1280/1920/2560） ──► ML Kit ──► 结果
```

改成**两段管线**：

```
全帧低分辨率 ──► ML Kit（已有：enableAllPotentialBarcodes 能给出候选框）
                    │
                    ├─ 有解出的码 ──────────────────────► 直接采纳（快路径）
                    │
                    └─ 只有「潜在条码」候选框
                            │
                            ▼
                    按 boundingBox 裁 ROI（外扩 15% 留白）
                            │
                            ▼
                    缩放到满足 ≥2px/unit（EAN-13 目标 ≥190px 宽，取 2 倍安全系数）
                            │
                            ▼
                    再送一次 ML Kit ──► 结果 / 帧内投票
```

### 4.2 为什么这比「继续抬全帧分辨率」好

| | 抬全帧到 2560×1440 | ROI 精读 |
|---|---|---|
| 解码器处理像素 | 3.7 M | 约 0.1–0.3 M |
| 内存峰值 | 高（YUV + Bitmap 双份） | 低 |
| 对小码的等效放大 | 2×（相对 1280） | **可到 4–8×**（只作用于目标区域） |
| 发热 | 明显 | 轻微 |
| 对 1D 码的作用 | 提升有限（1D 靠横向分辨率，整帧缩放收益被摊薄） | **直接作用于码的横向像素** |

现有三档分辨率**保留**，作为「粗检段」的档位；ROI 精读是叠加在它之上的**第二段**。

### 4.3 落地要点

- 候选框来源：`Barcode.boundingBox`（潜在条码也有）。注意做**坐标变换**：
  ML Kit 的坐标是「已按 rotation 摆正后」的图像坐标，裁剪时要对回原始 buffer。
  项目已有 `ImageSampling` 相关逻辑可参考，但需仔细核对——这是最容易出错的一处。
- **每帧只精读最多 1–2 个 ROI**，否则延迟失控。
- 精读结果与粗检结果合并时，走**同一套去重**（`CodeAdmission` + `DedupeTracker`），
  不要另开一条通路——否则同一个码会被计两次。
- 加开关（默认开），归入设置面板「识别」页，与「增强识别」并列。

## 5. P0-2：校验位自校验（推荐）

### 5.1 为什么这个最能提高「准确率」

用户原话是「提高识别**准确率**」。这个词有歧义，但在**盘点**场景里，
**误识（false positive）比漏识更致命**：漏识补扫一次即可，误识会直接把错误数据写进库存。

行业数据（Scandit 对比页）称 ML Kit 的误识率「5% 或更高」，
而商业 SDK 能做到 0%。这个数字有商业动机，但方向可信：**免费方案确实会误识**。

### 5.2 可自校验的码制

| 码制 | 校验方式 | 实现成本 |
|---|---|---|
| EAN-13 / EAN-8 / UPC-A | mod-10 加权校验位 | ~15 行 |
| Code-128 | mod-103（含起始符 + 校验符） | ~40 行 |
| Code-39 | 可选 mod-43（多数不启用） | ~30 行 |
| QR / Data Matrix | 内建 Reed-Solomon 纠错，ML Kit 已解 | 无需（库已保证） |

**EAN-13 + UPC-A + Code-128 覆盖了盘点场景的绝大多数**，加起来不到 100 行纯逻辑，
可以做成 `domain/ChecksumVerifier.kt`，配 20+ 个单测用例（含已知的合法码、
被改一位的非法码、前缀 0 的边界）。

不通过校验 → **丢弃该结果并记一条 debug 日志**，不弹提示（避免干扰）。
可按设置项选择「严格（丢弃）」或「宽松（接受但标记）」。

### 5.3 顺带的收益

一旦有了本地校验，可以做**「帧内多数表决」**：同一帧解出多个结果时，
校验通过的优先；都通过则按格式优先级（2D > 1D）。

## 6. P1 级措施

### 6.1 CLAHE + 轻锐化（只在 ROI 上做）

行业标准预处理链（物流分拨中心实测把识别率从 92.3% 提到 98.7%，
其中光照自适应是三大措施之一）：

```python
# CLAHE：对比度受限自适应直方图均衡化
lab = cv2.cvtColor(image, cv2.COLOR_RGB2LAB)
l, a, b = cv2.split(lab)
clahe = cv2.createCLAHE(clipLimit=3.0, tileGridSize=(8, 8))
# 轻锐化（unsharp mask）——对轻微失焦有效
blur = GaussianBlur(gray, (3, 3), 0)
sharp = gray * 1.5 - blur * 0.5
```

关键：**在全帧上做这些是浪费，只在 ROI 上做**。
并且锐化**不能过头**——过度锐化会把传感器噪声放大成条纹，反而干扰解码。
（这是实践里反复提到的教训。）

Android 上可以用 `RenderScript`（已废弃）或直接手写像素循环。
考虑到要单测，建议做成**纯函数**：输入 `IntArray` 像素 + 宽高，输出增强后的 `IntArray`。

### 6.2 多帧投票

同一码值连续 2~3 帧结果一致才采纳：
- 提升**准确率**（单帧的偶发误识会被后续帧否决）
- 提升**抗抖动**（运动模糊时单帧可能解错，多帧融合更稳）
- 代价：响应延迟从「1 帧」变成「2~3 帧」。**与现有 `DedupeTracker` 时间窗要协调**，
  不能让投票期超过时间窗，否则用户会觉得「扫了没反应」。

实现为状态机，纯逻辑可单测。

## 7. 建议的实施顺序

1. **P0-2 校验位** —— 先做这个。纯逻辑、零风险、可完全单测，立刻降低误识。
2. **P0-1 ROI 二次精读** —— 真正提升小码识别率的那一项。工作量中等，
   但坐标变换是坑，需要真机验证。
3. **P1 多帧投票** —— 与 P0-2 配合最好。
4. **P1 图像增强** —— 收益依赖场景，最后做，且要能单独关掉。

四项都建议**加设置开关、默认值保守**（延续 v1.4 的原则：默认行为不变，
用户主动开启才变）。
