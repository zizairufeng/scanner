# v1.8.8 — 相机页闪退：往已关闭的线程池投任务

> 用户反馈：「我的 scan app，出现闪退。帮我分析一下日志并修复。」
>
> 日志包 `ScanStock-logs-20261111_091824.txt`（1.8.7 / versionCode 20 /
> OnePlus PJX110 / Android 16 API 36）。
>
> 结论：**不是识别算法的问题，也不是内存问题**。相机页销毁时先把线程池关了，
> 而「CameraX 的最后一帧」和「ML Kit 在途识别的回调」还会往那个池子里投任务，
> 默认的 AbortPolicy 当场抛 `RejectedExecutionException`，抛在**主线程**上 → 进程被杀。

## 一、现场

崩溃报告 `crash-2026-11-11_091819-main.txt`：

```
崩溃线程: main (id=2)
内存: heap used=45MB max=256MB          ← 内存完全正常，不是 OOM

java.util.concurrent.RejectedExecutionException:
  Task C.j@5f9a772 rejected from
  java.util.concurrent.ThreadPoolExecutor@7d37c3[
      Terminated, pool size = 0, active threads = 0,
      queued tasks = 0, completed tasks = 661]
    at java.util.concurrent.ThreadPoolExecutor$AbortPolicy.rejectedExecution
    at java.util.concurrent.Executors$DelegatedExecutorService.execute
    ...
    at android.os.Handler.handleCallback          ← 主线程
```

用构建产物里的 `mapping.txt` 反查堆栈里的短名（该 mapping 属于 1.8.4，
1.8.7 的 R8 命名有位移，所以只取能对上的部分作参考）：

| 混淆名 | 真实类 | 说明 |
| --- | --- | --- |
| `c3.n` | `com.google.android.gms.tasks.zzh` | Play Services Task 的回调派发器，内部 `DelegatedExecutorService` |
| `c3.p` | `com.google.android.gms.tasks.zzw` | `TaskImpl` |
| `B.a` | `androidx.camera.core.impl.utils.executor.DirectExecutor` | 「就地执行」，即回调落在调用线程 |
| `C.j` | `androidx.camera.core.impl.utils.futures.Futures$CallbackListener` | CameraX 的 Future 回调包装 |
| `o2.d` / `o2.b` | `AppLog` / 崩溃处理器 | 写报告的我们自己，只是记录方 |

要点：**`Terminated, pool size = 0`** —— 这个单线程池已经 `shutdown()` 完成。
`completed tasks = 661` 与「81 秒、约 8fps」的帧量吻合，它就是一个**每帧派发一次**的执行器。

## 二、根因

`CameraPreviewCard.kt` 里，分析执行器与分析器、扫描器都在同一个 `DisposableEffect` 里创建，
`onDispose` 负责拆除。1.8.7 的拆除顺序是：

```kotlin
onDispose {
    disposed = true
    analyzerHolder = null
    runCatching { provider?.unbindAll() }   // ②  解绑用例
    analyzerExecutor.shutdown()             // ③  立刻关池子
    runCatching { scanner.close() }         // ④  最后才关 ML Kit
}
```

两个问题叠在一起：

1. **顺序反了。** 池子在 ML Kit 还在跑的时候就被关了（③ 早于 ④）。
   ML Kit 的 `process()` 是异步的，`shutdown()` 那一刻在途的识别任务完成回来要投递回调，
   目标执行器已经是 `Terminated`。
2. **裸 `Executors.newSingleThreadExecutor()` 用的是 AbortPolicy。**
   往终止的池子 `execute()` 不是「静默丢弃」，而是**当场抛异常**。
   而 `BarcodeAnalyzer` 里这行：

   ```kotlin
   scanner.process(inputImage)
       .addOnCompleteListener(workExecutor) { ... }   // ← workExecutor 已关闭 → 抛
   ```

   异常会落在**正好在调它的那个线程**上。本次是主线程（CameraX 的 Future 回调经
   `DirectExecutor` 就地执行），于是主线程未捕获异常 → 进程直接被杀。

另外 `analyze()` 本身没有「已释放」闸门：页面销毁之后到达的帧仍会去调
`scanner.process()`，撞上已 `close()` 的扫描器是同一个下场。

## 三、修复（三道防线 + 一层兜底）

### 1. 执行器包一层：拒绝只记账，不抛

新增 `util/RejectionTolerantExecutor.kt`，只吞 `RejectedExecutionException`，
其它异常照常抛（把不该吞的也吞掉，等于把 bug 变成「悄悄不工作」）。
第一次和之后每 100 次记一条日志，防止刷屏。

```kotlin
val rawExecutor = Executors.newSingleThreadExecutor()
val analyzerExecutor: Executor =
    RejectionTolerantExecutor(rawExecutor, name = "camera-analyzer")
```

### 2. 拆除顺序改成「先停来源，再关池子」

```kotlin
onDispose {
    disposed = true
    analyzerHolder = null
    analyzer.release()                       // ① 立闸门：此后到达的帧直接放行
    runCatching { analysisUseCase?.clearAnalyzer() }  // ② CameraX 停止投递帧
    runCatching { provider?.unbindAll() }    // ③ 解绑用例
    runCatching { scanner.close() }          // ④ 关 ML Kit（内部线程与在途识别）
    rawExecutor.shutdown()                   // ⑤ 最后才关池子
}
```

### 3. 分析器加 `released` 闸门 + 提交失败兜底

- `analyze()` 第一行判 `released`，是就直接 `imageProxy.close()` 返回，绝不碰已关闭的扫描器；
- `scanner.process()` 用 `runCatching` 兜住（扫描器已关时不外抛）；
- `addOnCompleteListener` 也用 `runCatching` 兜住。**这一步还有个隐蔽的必要性**：
  提交失败时没有任何监听器会来执行 `finally`，这一帧的 `ImageProxy` 就永远不关，
  CameraX 的背压闸门不放行 —— 表现为「画面还在动，但再也不识别」。
  所以失败路径里自己 `close()` 一次。

### 4. 兜底：全局异常处理器只拦「非主线程」的丢弃工作

`AppLog.installCrashHandler` 里加一条窄规则：沿 cause 链命中
`RejectedExecutionException`、**且不在主线程**时，不杀进程，改写一份 `swallowed-*.txt`
留证据（单独文件、单独计数，不混进崩溃报告；导出包里有独立段落）。

**为什么主线程例外**：异常已经把 `Looper.loop()` 的栈整个展开，handler 就算正常返回，
主线程也回不去了 —— 结果是「界面冻住 / ANR」，比带对话框的闪退更难查，
用户还会以为「没崩」。所以主线程这条路径只能靠上面三道防线堵住，
不能靠在最后一步假装没发生。这一条很关键，写在这里免得以后有人「顺手」把它加上。

## 四、顺手修掉的日志口径错误

崩溃报告里的「进程: 运行时长=195151s」是错的 ——
`SystemClock.elapsedRealtime()` 是**设备开机时长**，不是进程时长。
同一次启动的运行日志显示进程只活了 81 秒，两个数差 2000 倍，排查时白绕一圈。

现在拆成两行：

```
进程: pid=9439 本进程已运行=81s
设备已开机=195151s
```

同时补上相机生命周期日志（此前**完全没有**，导致「相机什么时候重建过」无从判断）：

- `相机初始化（分析档位=1280x720，增强识别=false）`
- `相机已绑定（档位=...，变焦上限=...，闪光灯=true）`
- `相机绑定失败`
- `相机释放（停止分析器 → 解绑 → 关扫描器 → 关执行器）`

## 五、验证

```bash
./gradlew :app:testDebugUnitTest     # 257 个用例，0 失败（新增 2 个）
tools/android-build/linux/build_release.sh
```

新增单测 `RejectionTolerantExecutorTest`：

| 用例 | 断言 |
| --- | --- |
| 未关闭时任务照常执行 | 任务跑 1 次、拒绝计数 0 |
| 关闭后提交只记账不抛异常 | 提交 3 次不抛、执行 0 次、计数 3 |

真机验证要点（需要在下次装机后确认）：

1. 连续扫码 → 切后台 → 回前台 → 反复进出设置改「分析档位 / 增强识别」，不再闪退；
2. 退出页面后日志里出现 `相机释放（…）`，且没有新的 `crash-*.txt`；
3. 若出现 `swallowed-*.txt`，说明还有别的地方在提前关池子，按里面的堆栈继续查。

## 六、未解决的疑点（诚实记录）

- 崩溃前 13 秒有一次 `onStop → onStart`，但日志里**没有** `onDestroy`，也没有
  「相机初始化」记录（1.8.7 不打这条日志）。因此**无法百分之百确定**这一次
  `shutdown()` 是由哪个事件触发的 —— 最可能是改「分析分辨率档位 / 增强识别」
  导致 `DisposableEffect` 重建（这两个值在 key 里），其次是权限状态翻转导致
  `if (granted)` 分支短暂离开组合。
- 但无论触发者是谁，**「往已终止的池子投任务会直接杀进程」这个缺陷是确定的**，
  修复后该路径不可能再引发闪退；且新增的相机日志能在下次复现时直接给出触发点。
