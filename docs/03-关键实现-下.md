# 三、关键实现（下）：去重、状态容器、列表、复制

## 3.6 条码解析与去重

`app/src/main/java/com/example/scanstock/domain/DedupeTracker.kt`（核心 10 行）

```kotlin
fun shouldAccept(key: String, nowMs: Long = SystemClock.elapsedRealtime()): Boolean {
    if (key.isEmpty()) return false
    synchronized(lock) {
        val last = lastReportedAt[key]
        val accept = last == null || nowMs - last >= windowMillis
        lastReportedAt[key] = nowMs      // ★ 无论 accept 与否都刷新时间戳
        maybePruneLocked(nowMs)
        return accept
    }
}
```

这一行 `lastReportedAt[key] = nowMs` 是整个去重逻辑成立的关键，值得展开：

- **ML Kit 的行为**：码在画面里，它每帧（约 30 次/秒）都会回调一次同一个 `Barcode`。不做去重，1 秒钟列表就多 30 条重复数据。
- **常见但错误的写法**：只在 `accept == true` 时更新时间戳。后果是——你把手机对着货架上同一个码不动，每过 1.5 秒它就往列表里塞一条，**依然刷屏**，只是频率从 30/秒 降到 0.67/秒。这正是需求里描述的「被同一条数据刷屏」现象，换个频率并不能解决。
- **本方案**：每帧都刷新时间戳。于是「持续可见」= 时间戳一直在被推后 = 永远进不了「距上次上报满 1.5 秒」的状态 = 不会被重复计入。只有当码**真的离开画面** 1.5 秒后再次出现，才会被计为新的一条。

顺带获得一个业务能力：**计件**。同一个条码扫一次 → 移开 → 再扫，会计入两条记录，正好对应「同一商品扫 5 件就是 5 条」。

### 跨帧去重是可关闭的

`DedupeTracker` 只管「时间窗」这一半。真正的准入判定收在 `CodeAdmission.admit()` 里，两级串联：

`app/src/main/java/com/example/scanstock/domain/CodeAdmission.kt`

```kotlin
fun admit(
    decoded: List<DetectedCode>,
    dedupeEnabled: Boolean,
    dedupe: DedupeTracker,
    nowMs: Long
): List<DetectedCode> {
    if (decoded.isEmpty()) return emptyList()
    val seenInFrame = HashSet<String>(decoded.size * 2)
    val accepted = ArrayList<DetectedCode>(decoded.size)
    for (code in decoded) {
        if (!seenInFrame.add(code.value)) continue                             // ① 同帧去重：无条件
        if (dedupeEnabled && !dedupe.shouldAccept(code.value, nowMs)) continue // ② 跨帧：受开关控制
        accepted += code
    }
    return accepted
}
```

- **① 同帧去重恒定生效**，不随开关放开。它挡的是「同一次拍摄内的重复」：一张照片里若有 5 个一模一样的二维码，关掉开关也不该一次记 5 条。
- **② 跨帧去重**受 `ScanUiState.dedupeEnabled` 控制。关闭时**根本不会调用** `shouldAccept()`，因此也不会写入时间戳——这点很关键：若关闭期间写了时间戳，那么「关 → 开」的瞬间，刚扫过的码会被判为「窗口内出现过」，表现为开关刚打开时前 1.5 秒毫无反应。ViewModel 在切换开关时还会额外调一次 `dedupe.reset()`，双保险。
- 抽出独立对象的另一个理由：`ScanViewModel` 继承 `AndroidViewModel`，依赖 Android 框架，跑不了纯 JVM 单测；放到 domain 层后这 12 条准入规则全部可被 `CodeAdmissionTest` 覆盖。

时间源用 `SystemClock.elapsedRealtime()` 而不是 `System.currentTimeMillis()`：前者是开机以来单调递增的毫秒数，用户扫码过程中系统自动对时、或跨时区，都不会让去重窗口错乱。

内存安全：`lastReportedAt` 会随扫过的不同码值增长，所以 `maybePruneLocked` 在条目超过 512 且距上次清理超过 30 秒时，清掉「超过窗口 10 倍时间没再出现」的键。正常盘点几千个 SKU 也不会涨到危险的量级。

在 ViewModel 中的调用点（`ScanViewModel.onCodesDetected`）：

```kotlin
val nowElapsed = SystemClock.elapsedRealtime()
val nowWall = System.currentTimeMillis()

val admission = CodeAdmission.admit(
    decoded = decoded,
    dedupeEnabled = _uiState.value.dedupeEnabled,
    dedupe = dedupe,
    nowMs = nowElapsed
)
if (admission.isEmpty()) return   // 全是重复帧 → 静默丢弃，不触发震动/提示音

val timeText = formatTime(nowWall)   // 同一次回调内时间戳必然相同，只格式化一次，省掉 N 个 SimpleDateFormat
val accepted = admission.map { code ->
    ScanItem(seq = nextSeq++, formatId = code.formatId, formatName = code.formatName,
             value = code.value, timeMillis = nowWall, timeText = timeText)
}
```

注意 `if (accepted.isEmpty()) return` 的位置在**触发反馈之前**：同一帧的重复回调、1.5 秒内的重复回调都不会震动。否则连续扫描时马达会一直嗡嗡响。

## 3.7 状态容器（StateFlow，UI 不可直写）

`app/src/main/java/com/example/scanstock/ui/ScanViewModel.kt`（节选）

```kotlin
private val _uiState = MutableStateFlow(ScanUiState())
val uiState: StateFlow<ScanUiState> = _uiState.asStateFlow()

// 一次性事件：replay = 0，避免旋转屏幕后重放「已复制 N 条」
private val _events = MutableSharedFlow<UiEvent>(
    replay = 0, extraBufferCapacity = 16, onBufferOverflow = BufferOverflow.DROP_OLDEST
)
val events: SharedFlow<UiEvent> = _events.asSharedFlow()

_uiState.update { state ->
    state.copy(items = state.items + accepted, lastValue = accepted.last().value,
               flashTick = state.flashTick + 1)
}
```

为什么状态更新集中在 ViewModel：

- `MutableStateFlow.update {}` 内部是 CAS 重试循环，**任何线程调用都安全**。分析回调在主线程、相册解码在 `Dispatchers.IO`，两条路径汇入同一个 `update`，不需要额外加锁。
- `ScanItem` 是 `data class` 且 `items` 用 `+` 生成新列表，Compose 能精确判断哪些行需要重组（配合 `items(key = seq)`）。
- **ViewModel 不含 UI 类型**，剪贴板写入被推给 UI 层（见 3.9），旋转屏幕后状态天然保留。

## 3.8 结果列表 UI

`app/src/main/java/com/example/scanstock/ui/components/ResultListPanel.kt`（节选）

```kotlin
LazyColumn(
    state = listState,
    contentPadding = PaddingValues(start = 12.dp, end = 12.dp, top = 6.dp, bottom = 96.dp),
    verticalArrangement = Arrangement.spacedBy(6.dp)
) {
    items(items = items, key = { it.seq }) { item -> ResultRow(...) }
}

// 只在条数增加时滚到底部（用户上滑翻历史时 size 不变，不会被强行拽回去）
LaunchedEffect(items.size) {
    if (autoScroll && items.isNotEmpty()) listState.scrollToItem(items.lastIndex)
}
```

三个细节：

1. **`key = { it.seq }`**：序号全局唯一且稳定。连续盘点轻松上千条，没有稳定 key 时中间插入会让整表重组、滚动位置乱跳。
2. **`scrollToItem` 而非 `animateScrollToItem`**：高频追加（一秒好几条）时动画会互相打断，观感反而卡顿。
3. **`bottom = 96.dp` 的 contentPadding**：给底部按钮栏留出净空，否则最后一条会被「复制全部」挡住点不到。

每行结构：`序号徽标 | 码值（等宽字体，最多 2 行省略）+ 码制/时间 | 删除按钮`。
**整行可点 = 复制这一条**——这是盘点时频率最高的操作，做成整行热区，单手戴手套也能点中。删除按钮用 `IconButton` 单独放在右侧，与整行点击不冲突。

## 3.9 复制逻辑

`app/src/main/java/com/example/scanstock/domain/CopyFormatter.kt`（全量核心）

```kotlin
fun format(items: List<ScanItem>, format: CopyFormat): String {
    if (items.isEmpty()) return ""
    return when (format) {
        CopyFormat.NUMBERED_TAB -> items.joinToString("\n") { "${it.seq}\t${it.value}" }
        CopyFormat.PLAIN        -> items.joinToString("\n") { it.value }
        CopyFormat.CSV          -> buildCsv(items)
    }
}

internal fun csvEscape(raw: String): String {
    val needQuote = raw.any { it == ',' || it == '"' || it == '\n' || it == '\r' }
    if (!needQuote) return raw
    return "\"" + raw.replace("\"", "\"\"") + "\""
}
```

- **默认格式是纯文本**（`CopyFormat.PLAIN` 排在枚举首位，枚举顺序即设置面板显示顺序，`ScanUiState.copyFormat` 默认取它）：每行只有码值，粘进聊天窗口、搜索框、任意文本框都不会带出多余字符，是覆盖面最广的形态。当前格式直接显示在底部按钮上（「复制全部 (12) · 纯文本」），不必进设置确认。
- **需要两列对齐时切「序号+Tab」**：粘进 Excel 会自然分成两列，适合对账。
- **行分隔符硬编码 `\n`**：不用 `System.lineSeparator()`。Windows 的 `\r\n` 粘到 Excel 里会在单元格内留下不可见的 CR，某些 WMS 导入会因此判为脏数据。
- **单条复制固定只复制码值**（`formatSingle`）：用户点某一条时，99% 是想把码值贴进搜索框或聊天窗口，带序号和 Tab 反而是负担。
- **CSV 转义按 RFC 4180**：条码内容本身一般不含逗号，但 QR 码内容是任意文本（可能是 JSON、含逗号与引号），不转义必然把 CSV 结构弄坏。
- **不写 UTF-8 BOM**：理由见假设第 4 条。

剪贴板写入放在 UI 层（`ScanScreen.kt`），因为它是 UI 语义、需要 `Context`：

```kotlin
LaunchedEffect(Unit) {
    viewModel.events.collect { event ->
        when (event) {
            is UiEvent.CopyToClipboard -> {
                val ok = context.copyToClipboard(event.text)
                val message = when {
                    !ok -> "剪贴板不可用，复制失败"
                    // 单条复制永远只有码值，与「复制全部」的格式设置无关，提示语不并列格式名
                    event.isSingle -> "已复制该条码值"
                    else -> "已复制 ${event.itemCount} 条（${viewModel.uiState.value.copyFormat.label}）"
                }
                snackbarHostState.showSnackbar(message)
            }
            is UiEvent.Message -> snackbarHostState.showSnackbar(event.text)
        }
    }
}

private fun Context.copyToClipboard(text: String): Boolean {
    val manager = getSystemService(Context.CLIPBOARD_SERVICE) as? ClipboardManager ?: return false
    return runCatching { manager.setPrimaryClip(ClipData.newPlainText("scan_result", text)) }.isSuccess
}
```

- `UiEvent.CopyToClipboard` 带一个 `isSingle` 标志：单条复制与「复制全部」的格式设置**无关**（永远只有码值本身），所以提示语单独写成「已复制该条码值」、不并列格式名——否则把「复制全部」设成 CSV 后，点单条会弹「已复制 1 条（CSV）」，属明显误导。
- 用 `runCatching` 包住：极少数定制 ROM 会禁用剪贴板服务，`setPrimaryClip` 抛异常会直接崩掉正在进行的盘点。失败时给一条可读提示，列表数据仍在。
- Android 13+ 系统自己会弹「已复制」气泡；我们仍显示 Snackbar，因为它额外告知了**条数与格式**，这是系统气泡没有的信息。
